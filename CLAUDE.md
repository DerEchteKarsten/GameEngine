# GameEngine

Vulkan game engine in Rust (edition 2024, uses unstable `#![feature]`s), built on bevy 0.19 ECS **without** bevy's renderer.

## Orientation: read this before exploring
- A **code map** (each file's purpose, key types, and plugins, plus a shader table and live git state) is injected at session start by a `SessionStart` hook. Check it before running `ls`/`rg`.
- Full pub signatures and struct fields live in `.claude/context/api/{lava,core,game,lava-macros}.md`. Read the relevant file instead of grepping for an API.
- These files are generated by the `tools` workspace crate (`tools/`, no `#![feature]`s, so stable cargo works). To refresh them by hand, run `cargo run -q --release -p tools --target-dir target/tools`. It uses its own target dir so it never blocks on the main build lock, and it's cached by mtime.
- **Subagents don't get the hook output.** When delegating exploration, tell the subagent to read `.claude/context/codemap.md` first.
- Every `.rs` file starts with a one-line `//!` doc that feeds the code map. Keep it accurate when a module's role changes, and add one to every new file.

## Crates (dependency order)
- `lava-macros`: proc macros for lava (validation tracing).
- `lava`: Vulkan abstraction over `ash` + `gpu-allocator`. Global `Ctx` state, bindless descriptors (`BindlessHandle`; lava keeps no index bookkeeping, see Bindless slots), `lava::init(Option<display>)` (`None` = headless), per-window `Surface` + `Swapchain` objects, usage-typed `Buffer`/`BufferSlice` and `Image`/`ImageView` (type-state generics `F: Format`, `U: *Usage`), `CommandBuffer` with automatic barrier tracking (every image access asks for `GENERAL`, except attachments, which are in `ATTACHMENT_OPTIMAL` while drawn to; a pending write gets no second barrier for stages and accesses an earlier barrier already made it visible to, and a layout transition waits only for its image's tracked accesses, or for everything when there are none, so a frame loop hands the `PendingAccesses` that `Frame::execute` returns to its next frame), and `compute`/`raytrace`/`raster` dispatch. A generated `Pass::push_bindings(...)` returns a `BindingOutput<K>` (push constants, specialization constants and accesses; a pass with specialization constants returns an `IncompletePass` that `.constant_bindings(...)` completes; the zero-sized `kind::{Compute, RayTracing, RasterVertex, RasterMesh}` marker decides where it can be recorded). `cmd.raster(extent)` starts one rendering: `color_attachment(view, clear)`/`depth_attachment(view, clear)`, then any number of `draw`/`draw_indexed`/`draw_indirect(_count)`/`launch(_indirect)` calls, each with its own `RasterState` (`blends([..])`, one `Blend::{Replace, Alpha, Add, Attenuate, Skip}` per colour attachment, default all `Replace`; `depth_write`; `backface_culling`; `wire_frame`), and `record(name)` records them in one rendering under one GPU scope. Within a rendering, depth and blending follow draw order without barriers, but nothing else does, so no draw may read what an earlier one writes. The draw count is part of the type, so a draw that may not happen is recorded with a count of 0 (direct draws of 0 instances are skipped).
- `core`: engine library made of bevy plugins wired in `core/src/lib.rs::CorePlugin`. It covers assets (the scene/material/mesh/texture files, their loaders, and the `bake` tool in `core/src/bin` that makes them from glTF), the render sub-app (pipelined, `ExtractSchedule`), a custom immediate-mode UI with docking, the editor (gizmos, picking, console, asset browser), the profiler, physics (BVH raycasts), and the scene.
- `game`: the game binary (spawns a camera) plus the headless `render` tool in `game/src/bin` (see Headless tools).
- `tools`: dev tool that generates the Claude Code context (code map + API files) from the sources.

## Coordinates
- World space is left-handed with +Z up, +X forward and +Y right (Unreal's convention). A camera looks along its local +X; `update_camera` (`scene/camera.rs`) turns that into Vulkan's view space (+Y down) and uses a reversed-depth `perspective_lh`, and `ray_direction` inverts exactly that. Don't use bevy's `forward()`/`up()`/`right()`/`looking_at`, which assume -Z forward and +Y up; rotate `Vec3::X`/`Y`/`Z` instead.
- The bake converts glTF (right-handed, +Y up) by swapping Y and Z in positions, normals and node transforms, and flips the triangle winding, so front faces are clockwise on screen (lava's `FrontFace::CLOCKWISE`). Changing this needs a bake with `--force`.

## Viewport
- With the editor, the scene is rendered into an offscreen image in the swapchain format (`ViewPortTarget` in `core/src/render/render.rs`) that starts at the initial window size and only grows; the scene uses its top-left `rect.size()` pixels, the passes get that size as an argument, and the tab draws it with matching UVs (`ViewPort.image_size`). `extract_view_port` writes its bindless handle into the main world's `ViewPort`, and the tab (`editor/viewport.rs`) draws it as a UI image. `ViewPort.rect` is the tab's content area; `hovered`/`focused` gate picking, drops and camera input. `paused` (the "Pause Viewport" button in Render Settings) makes `record_frame` skip the scene passes; the tab keeps showing the last image.
- Without `EditorPlugin` there is no `ViewPort`, and the same passes draw straight into the swapchain image.
- An empty `DockingNode` leaf (`window: u32::MAX`) is just free space; a window dropped on it fills it.
- Since bevy 0.19 resources are entities: the Hierarchy tab lists them by type name (`IsResource`), the Selected tab edits the reflected ones like any component, and the Delete key skips them. To make a resource editable, derive `Reflect` with `#[reflect(Resource)]` (auto-registered); a field that can't be reflected needs `#[reflect(ignore, clone)]`, because the tab works on a `reflect_clone` of the value every frame.
- UI windows have no open/close calls: `ui.build(label, …)` requests a missing tab (created next `PreUpdate`), and `update_windows` closes every tab that wasn't built during the previous frame. `windows.ron` is only layout memory: a saved window (rect, tab group, dock slot) is created when one of its tabs is first requested, and dock slots nobody requested in the first frame are pruned. A reopened tab returns to its last rect; on exit only open windows are saved.

## Headless tools (use these to check your work)
- **Render to a PNG:** `PATH=$HOME/.cargo/bin:$PATH cargo +nightly run -q -p game --bin render -- game/assets/sponza.scene.ron /tmp/out.png`, then Read the PNG. It takes any scene file inside `game/assets` (`.scene` or `.scene.ron`; to render several scenes together, write a `.scene.ron` of `SpawnScene` entities) and draws it at `--size WxH` (default 1280x720) under the game's sky from a camera at `--eye X,Y,Z` looking at `--target X,Y,Z` with a vertical `--fov DEG` (default: from 0,0,2 towards 10,0,3, 65°), once the scene, everything it references and the sky are loaded. Takes about 2 s for sponza. Write the PNG outside `target/`, which is denied for reading. `--frames N` renders N frames (the PNG is the last), `--profile DIR` profiles them (see Profiling) and prints the summary.
- It uses `HeadlessRenderPlugin { size }` (`core/src/render/headless.rs`), which only initialises lava: no window, swapchain, UI, console or render sub-app. Once the scene is loaded, `render_frame(main_world, &settings)` runs the extract systems on a render world it keeps (with its queue, frame slot, pending accesses, target and readback buffer) in the main world, draws the scene passes (`record_scene` in `render.rs`, shared with the windowed frame) into an RGBA8 image and copies it into the readback buffer; `read_pixels(world)` returns the last frame's pixels (reading that host-visible buffer takes about 10 ms, so it isn't done per frame).
- **Bake assets:** `PATH=$HOME/.cargo/bin:$PATH cargo +nightly run -q --release -p core --bin bake -- [--force] [FILE...]` turns every `.glb`/`.gltf` in `game/unbaked_assets` (`core::UNBAKED_ASSET_DIR`) that is newer than its baked scene into files in `game/assets`, and every `.exr` into a `.tex` of the same name. It uses no bevy app and no GPU (sponza: about 50 s, 2.3 GiB peak memory, 462 MB baked). The meshlet build is not deterministic, so a rebake changes the mesh files (and a few pixels).
- **Bake assets** writes binary files; add `--ron` to also write `.scene.ron` and `.mat.ron` next to them for reading. The render tool loads either layout.

## Profiling
- Everything below is the `profiling` cargo feature (default on in `lava`, `core` and `game`; `core` and `game` depend on the crate below without default features). Without it (`cargo run -p game --no-default-features --features dynamic_linking`) there is no `core::profiler` module, no `ProfileLayer`, `FrameSlot::set_profiling` does nothing, `VK_KHR_shader_clock` isn't enabled, and the Slang session (`lava/src/slang_compile.rs`) leaves out the `PROFILING` macro, so `PROFILE(...)` compiles to nothing. Gate new profiler code with `#[cfg(feature = "profiling")]`. Disabled at runtime, the profiler cost about 0.04 ms wall and 0.1 ms CPU per frame over leaving it out.
- `ProfilerPlugin` (`core/src/profiler`) keeps the times of the last `MAX_FRAMES` in `Profiler.times` (plain values: wall, CPU, GPU), plus the GPU scopes and shader times of those frames in fixed rings tagged with their frame number; a frame is the time between two runs of `end_frame` (`Last`), numbered by `capture::frame()`. The game adds it in `main.rs`; the editor's "Profiler" tab needs it. `Profiler::set_enabled(false)` (the tab's "Profile" checkbox, or `ProfilerPlugin { enabled: false, .. }`) stops span capture, GPU queries and shader clocks; frames then only have their wall time.
- CPU: `capture::ProfileLayer` writes every span entered on any thread, when it ends, into that thread's fixed ring (`SPANS_PER_THREAD`, a `head` atomic, no lock; old spans are overwritten), as a `SpanKind`: bevy's "system" (systems and run conditions) and "schedule" spans are named by their `name` field, any other span by its name plus its `name`/`pass` fields (e.g. `system_commands <system>`, `compute BvhCull`). A span belongs to the frame it started in (`CpuSpan.frame`). The rings are read only while recording is off (paused): `capture::for_each_thread` skips the slots the at most `MAX_DEPTH` spans still open at the pause can overwrite. There is no live profile: `Profiler::select(i)` (a click in the tab's graphs) pauses and scans every ring once to build the one `Profiler.selected` `FrameProfile` (spans per thread, GPU scopes, shader times); `save` builds all of them once.
- CPU vs GPU time: the wall frame time includes waiting, so a span where a thread blocks on the GPU or another thread gets a `wait = true` field (`SpanKind::Wait`): the frame slot fence, swapchain acquire, present, and the main thread's wait for the render thread in `renderer_extract`. Mark any new blocking call the same way. A thread's busy time is the time covered by its spans minus its wait spans; the CPU time is the busiest thread's, since main and render thread run in parallel. While recording, per-thread atomic counters add each span's own time (minus its children) to the frame it started in, and `end_frame` reads them two frames late. Pausing replaces them with the exact time in each frame's window, from `capture::busy_signs`, which finds a span's recorded parent by depth and containment (bevy's `bevy_app` span never ends, so its children are the roots). The GPU time is the root scope's timestamps. The summary says which bounds the frame.
- `core::register_tracing()` installs the subscriber (console, stderr and profiler layers); the game calls it first in `main`, because bevy creates a system's span when the system is added and a span created before the subscriber exists never records. `ConsolePlugin` calls it if `main` didn't. The `render` tool installs its own subscriber with `ProfileLayer`.
- `bvh_cull.slang`'s node queue (`bvh_node_stack`, `~0` = empty) and meshlet batch counters (`meshlet_batches`, 0) are filled once (`RenderResources.fresh`, set again when the attachments grow): it writes every slot and counter it consumes back to that value. `candidate_meshlets` is never filled; only published batches are read. On this iGPU (Intel Arc B390, shared LPDDR5X) every MB a pass writes costs about 7 µs, so avoid per-frame fills and clears of big resources.
- **Benchmark view** (the worst case found in sponza, about 10k meshlets drawn): measure performance changes with it, in release builds, comparing CPU, GPU and per-pass times against a run of the old build:
  `PATH=$HOME/.cargo/bin:$PATH cargo +nightly run -q --release -p game --bin render -- game/assets/sponza.scene.ron /tmp/bench.png --eye -12.44,-0.21,2.61 --target -3.31,-0.21,6.69 --fov 64.7 --size 2560x1440 --frames 120 --profile /tmp/bench`. After a shader change, the first run compiles every pipeline into Mesa's cache (its first frame then takes several hundred ms), so run it twice and judge frame times by the median.
- The B390's clock moves between 900 and 2500 MHz from run to run and within a run (`act_freq` in `/sys/class/drm/card0/device/tile0/gt0/freq0/`), and the same frame takes about 2.5 times as long at 900. Compare GPU times only at the same clock: alternate the variants' runs and read `act_freq` after every frame.
- GPU: a `FrameSlot` with `set_profiling(true)` times every compute and ray tracing pass (named by its generated struct), every rendering (named by `record(name)`: "Scene", "Outline", "UI", "Gizmos") and every `cmd.begin_scope(name)`/`end_scope()` group (also debug labels), under a root scope "frame", with pipeline statistics (task/mesh/fragment/compute invocations) per pass; clipping counts aren't allowed while mesh shaders draw. The results come back in `Frame::last_timings()` (`FrameTimings`) when the slot is begun again.
- Shader clocks: entry points except fragment shaders start with `PROFILE(PROFILE_COMPUTE/TASK/MESH/VERTEX)` (`shaders/include/profile.slang`), which counts only in a pass that `#define USE_CLOCKS` before its first include of `profile.slang`; elsewhere it is empty, so shared code (`scene_mesh`) can call it, and the pass gets no clock constant or counter binding. It adds each subgroup's `VK_KHR_shader_clock` ticks, plus one subgroup packed above `PROFILE_TICK_BITS`, with a single atomic to one of 64 striped counters in descriptor set 2 (`lava::profiling`, one cache line per stripe), keyed by the pass index (`PROFILE_PASS`, which the Slang session defines per pass). The L2 serialises the atomics to a cache line (about 200 cycles each on the B390), so a full-screen pass of 30k subgroups pays about 0.1 ms per atomic per subgroup; two of them were the biggest part of the tonemap's time, so never add a second one. Counters only grow and wrap; each profiled slot reports the difference since the last read as `ShaderTime`s, so nothing waits. The ticks are about core clock cycles and summed over parallel subgroups, so the report shows each pass's share of shader time rather than ms. Fragment shaders stay out: a buffer write disables early depth testing even while profiling is off (it raised Raster's fragment invocations by 30%). Without `shaderSubgroupClock`, instrumented pipelines can't be created. The windowed `render()` profiles its slots while the render world has `GpuTimings`, per frame slot (reusing their buffers), which `extract_gpu_timings` hands to `Profiler::add_gpu`; they join the frame that ran when they were submitted, a few frames later. GPU memory comes from `lava::profiling::memory_report()`.
- Output: the editor's Profiler tab shows live frame/CPU/GPU graphs; the selected frame gets a timeline and its GPU scope, shader time and CPU span tables (filterable by kind). `Profiler::save(dir)` writes `profile.txt` (frame times, GPU scopes, top 25 CPU spans, memory) and `profile.json` (Chrome trace for Perfetto). The tab's "Save capture" writes to `profiles/<unix time>/`, `GAME_PROFILE=DIR[:FRAMES] cargo run -p game` saves the first FRAMES frames (default 300), and `render --frames N --profile DIR` the headless frames.

## Performance conventions
- No heap allocation per frame at steady state: reuse buffers (`clear`, `clone_from`, fixed-capacity rings, scratch `String`s), allocate once up front.
- Data shared between threads on a hot path is synchronised with atomics, not mutexes.
- Expensive derived data (profiles, reports, tables) is computed on demand, once, and kept until its input changes; nothing is rebuilt every frame just to be displayed.
- Full-screen compute passes are bound by memory, not arithmetic: keep the default 8x8 workgroup (Intel's tiled layouts hold a 2D block of texels per cache line, so a subgroup covering a 32-pixel row cost 20% more than an 8x4 tile), and several pixels per lane or hoisting the loads above the branches gained nothing once the profiler's atomic was down to one per subgroup.

## Bindless slots
- Lava never picks a descriptor index: `Image::new`/`with_mip_levels` make an unbound image (null `handle`), `new_sampled`/`new_storage`/`new_unified` (gated by the `SampledBinding`/`StorageBinding`/`UnifiedBinding` usage traits) create and bind it, and `bind_*` record into a `BindlessWrites` that `submit`s many writes in one `vkUpdateDescriptorSets`. A `Swapchain` never binds its images, also not after `recreate`: `bind_storage(first, …)` puts image `i` at `first + i`. `resize_swapchain` rebinds after every recreation, at the old slots unless the image count changed (Mailbox gets one more image here), in which case it frees them, takes new ones and adds `render_finished` semaphores. Both sets are `UPDATE_UNUSED_WHILE_PENDING`; dropping an image leaves its descriptor stale. Set 2 holds only the profiler's shader clock counters.
- `lava::image::on_drop(hook)` sets a global function every dropped `Image` calls with its handle. Core sets it in `bindless::init()` (right after `lava::init`) and gets its slots from `bindless::sampled_slot()`/`storage_slots(n)` (atomic counter plus free list per set), which the hook refills. Retired images (`Frame::retire`) drop only after their frame, so a grown depth attachment or viewport target never reuses a slot a pending frame reads.
- Textures sit at `TEXTURE_SLOTS_BASE + asset index` (`texture_index` in `assets/texture.rs`), known as soon as the handle exists. `write_texture_slots` (in `Last`) fills every texture slot with a white placeholder on its first run, then follows `AssetEvent<GpuTexture>`: a loaded or reloaded texture is written into its slot, a removed one is replaced by the placeholder. `scene_raster.slang` skips normal mapping when the normal sample is exactly (1, 1), which is the placeholder.

## Asset files and the asset browser
- There is no bevy asset processor and no `.meta` file: `asset_plugin()` loads `game/assets` unprocessed. The `bake` tool (`assets/bake.rs`) turns the default scene of `sponza.glb` into `sponza.scene` plus `sponza/{meshes,materials,textures}/<name>.{mesh,mat,tex}`, so every file loads on its own. A bake deletes and rewrites the scene's whole directory.
- The files have no magic or version: after changing a layout (or the `Material` struct), bake with `--force`. Binary files are written with the `write_slice`/`write_compressed` helpers in `assets/util.rs` and read back front to back through bevy's async `Reader` (`read_slice`/`read_compressed`); big payloads are zstd-compressed, structured ones are `postcard`.
- Scenes (`scene/file.rs`) store entities: a parent per entity (`u32::MAX` = the spawn root), the referenced asset paths (relative to the scene file; a leading `/` means the asset root), and one column per component type, named by `short_type_path`. `.scene` frames the head and then one postcard frame per column; `.scene.ron` lists the same data entity by entity. Handles are saved as indices into the assets, and loads start with `load_context.load` (deferred), so the scene is loaded right after its file is read. The bake writes the `Instance` column first.
- A component is saved if it implements `SceneComponent` (automatic for `Component + Clone + serde`; `Instance` does it by hand through `SaveCtx`/`LoadCtx`) and is registered with `ReflectSceneComponent` (`#[reflect(SceneComponent)]`, or `register_type_data` like `Transform`/`Name` in `ScenePlugin`). An unknown or ambiguous column name fails the load.
- Spawning: `SpawnScene { scene }` on an entity makes the exclusive `spawn_scenes` create the scene's entities as its descendants, then removes the component. It requires `Transform` and is a scene component itself (saved as an asset index), so a scene can place other scenes. The Hierarchy tab saves the selected entity's descendants to the typed path (relative to `ASSET_DIR`, `.ron` picks RON); materials without a file are written to `<scene>/materials/material_<n>.mat` first.
- The bake keeps the glTF node tree (local TRS, names, empty nodes); a mesh with several primitives gets one child entity per primitive. Lights, cameras, skins, morph targets, animations, non-triangle primitives, extra UV sets, texture transforms, GPU instancing and other scenes are dropped with a warning.
- `.mesh`: `MeshHeader`, the compressed GPU data, the compressed collision BVH. `.tex`: `TextureHeader`, a `PREVIEW_SIZE` RGBA8 preview, then one compressed mip after the other. Textures are BC7 (`TextureKind::Color` sRGB, `Data` linear) or BC5 (`Normal`, the shader reconstructs z), chosen by the material slot that uses the image. An OpenEXR file becomes BC6H (`Hdr`, unsigned half floats, no alpha); its preview is clamped to 1.
- The sky is the `Skybox` resource (`scene/mod.rs`), a `Handle<GpuTexture>` to an equirectangular texture (Z up, +X at u = 0.5 with u growing towards +Y, v = 0 at the top), editable in the Selected tab. `extract_skybox` hands its texture slot to `tonemap.slang`, or `NULL_HANDLE` until it is loaded, which draws a flat colour. The tonemap draws the sky where the depth is still cleared (0), and picks the mip from the angle between neighbouring pixels.
- The raster pass draws linear HDR colour into `RenderResources.hdr` (`R16G16B16A16Sfloat`, grown with the depth attachment), and blended materials go into the `accum`/`revealage` images (see Materials). The raster pass runs even without instances, because it clears the depth. `tonemap.slang` puts the sky where nothing was drawn, composites the blended layers over it and writes the result to the target with `RenderSettings.exposure`, an ACES fit and sRGB encoding, since the targets are UNORM shown as sRGB. Outlines and gizmos draw onto the target afterwards, untonemapped: `bvh_cull.slang` also writes the visible meshlets of `OUTLINE` instances into their own list (`OUTLINED_DRAW`), `raster_outline.slang` draws just those into the cleared depth, and `draw_outline.slang` colours the empty pixels near them.
- The browser (`editor/asset_browser.rs`) shows the files of `ASSET_DIR` as they are and keeps no per-tile state: only the rows in view are laid out, and a click opens a folder. Kinds match the end of the file name, case-insensitively. A `.tex` tile in view reads just its preview from the file, synchronously, into one main-world atlas image (`Previews`, written by `Image::copy_region_from`); the atlas holds 1024 previews and the least recently shown makes room.
- The browser never polls. A `notify` watcher on `ASSET_DIR` forwards every changed path (access events are ignored): the path's preview is forgotten, and a change directly inside the open directory re-reads it.
- Dragging carries an `AssetDrag` (`ui/dragdrop.rs`), which loads the asset only when a drop target takes it (`drop_in_viewport`, the inspector's handle slots).

## Materials
- A material is its own asset: `.mat` (postcard) or `.mat.ron`, holding `MaterialFile` (factors plus five optional texture paths relative to the file). `MaterialLoader` (`assets/material.rs`) shares one `MaterialState` with the `Materials` resource: a host-mapped buffer of `MAX_MATERIALS`, created on first use, and a free list. Each `GpuMaterial` owns a slot (`gpu` address, `cpu` pointer) and frees it on drop; the renderer writes `material.gpu` per instance (`Buf<Material *>` in `scene_raster.slang`).
- A material's texture indices are final when it loads (`texture_index` of the deferred texture handles), so nothing is written back when a texture arrives, and textures shared by path load once. A mesh dropped from the browser gets a default material from `Materials`.
- `MaterialSettings` exists only on `Selected` instances (systems in `scene/mod.rs`): it is read through `GpuMaterial.cpu` on selection, edits (factors and textures) are written straight back, and it is removed on deselect. Everything sharing the material sees the edit; it is not written back to the `.mat` file.
- `Material` (`shaders/include/datatypes.slang`, mirrored by `MaterialSettings` and `MaterialFile`) needs a bake with `--force` when it changes. `alpha_cutoff` discards fragments with less alpha; a negative cutoff blends instead. Scene meshlets are drawn only with mesh shaders (`VK_EXT_mesh_shader` is required), without a task shader (one was much slower here): `bvh_cull.slang` appends each visible meshlet to a list and counts a stride per `MESHLET_STRIDE` of them in that list's `MeshletDraw` (`TraversalVariables.draws`, indexed by `OPAQUE_DRAW`/`BLENDED_DRAW`/`OUTLINED_DRAW`), which `launch_indirect` takes as the mesh workgroup counts. Workgroup (x, y) draws meshlet x * `MESHLET_STRIDE` + y, so neighbours in the list are drawn apart, which drew fewer hidden fragments. `shaders/include/scene_raster.slang` holds the bindings, the `scene_mesh` entry point every scene pass shares (`MESH_THREADS` invocations per meshlet), and the material shading. Its `MAX_MESHLET_VERTICES`/`TRIANGLES` (128/128) are the limits of `build_meshlets` in `assets/mesh.rs`; changing them needs a bake with `--force`. `wirte_instances` packs each instance's `InstanceFlags` (`OUTLINE`, and `OPAQUE` from the material's cutoff every frame, so editing it switches the instance live) into `InstanceManager.flags`, `INSTANCE_FLAG_BITS` bits per instance; `datatypes.slang` mirrors the bits and reads them with `instance_flags`. `bvh_cull.slang` reads that bit per visible meshlet and writes blended meshlets into their own list (`BLENDED_DRAW`), which `record_scene` draws after the opaque ones, in the same "Scene" rendering (the opaque draw `Skip`s attachments 1 and 2, the blended one attachment 0), with `raster_blended.slang`: weighted blended order-independent transparency (McGuire and Bavoil 2013), so no sorting. Depth-tested without depth writes, it adds weighted premultiplied colour and weight into `accum` (`R32G32B32A32Sfloat`, since highlights times the weight overflow half floats) and multiplies `revealage` (`R16Sfloat`) by `1 - alpha`; both are cleared once (`RenderResources.fresh`), and after that `tonemap.slang`, which composites them over `hdr` and reads the 16-byte `accum` only where `revealage` < 1 (it is bandwidth-bound; `revealage` is read through the sampler as a `MutTex2D`), resets exactly those pixels, so nothing clears them every frame (a full clear cost more than the rest of the blended pass). Keeping the revealage in `hdr`'s unused alpha instead was measured slower: resetting it takes either storage writes to `hdr` (tonemap 0.01 ms faster, Scene 0.1 ms slower) or a per-frame clear (Scene 0.35 ms slower). The blended pass therefore discards fragments with alpha below 1/1024, which couldn't lower the half-float revealage and would never be reset. Overlapping layers of very different colour and high alpha mix instead of hiding each other. The importer sets 0 for opaque glTF materials, -1 for blended ones and for masks with a cutoff of 0.

## Shader pipeline
- Source: `shaders/passes/*.slang` (one file = one pass) and `shaders/include/*.slang`. `shaders/old/` is dead code.
- `lava/build.rs` compiles each pass with `shader-slang` (one session per pass, made by `lava/src/slang_compile.rs`, which `build.rs` includes by `#[path]` and hot reload shares, so both compile alike), writes SPIR-V to `$OUT_DIR/passes/`, and reflects the `[[vk::push_constant]]` struct and the specialization constants to **generate `lava/src/bindings.rs`** (gitignored, never edit it). For example, `raster_ui.slang` → `RasterUi::push_bindings(...).constant_bindings(...)` returns a `BindingOutput<kind::RasterMesh>` that you hand to `cmd.raster(extent)...launch(...).record(name)` (a compute pass's goes to `cmd.compute()`). Every pass pushes `MAX_PUSH_CONSTANTS_SIZE` (256) bytes, its struct zero-padded; `build.rs` rejects a bigger struct.
- Matrices use column-major layout (`matrix_layout_column` in both `build.rs` and the hot-reload session in `command_buffer.rs`), so a glam `Mat4` arrives untransposed and shaders write `mul(M, v)`.
- Push-constant field types map like this: `Buf<T>`/`MutBuf<T>` → `BufferSlice<T, U: IsStorage>`, and `Img` → `ImageView` (bindless handle): `Tex2D` reads through the sampler (`IsSampled`), `Image2D`/`MutImage2D` through the storage descriptor (`IsStorage`), and `MutTex2D` reads through the sampler but writes as storage (`UnifiedBinding`, an image bound in both sets). A typed load of a storage image costs several times a sampler fetch on Intel (it was a quarter of the tonemap), so read an image through the sampler whenever its usage allows. Inside structs behind a `Buf`, `Img` and `DynImg` fields become a `BindlessHandle`. `Img` and `DynImg` have `GetDimensions()`. `DynImg` (`bindless.slang`) reads whichever of the sampled/storage index isn't `NULL_HANDLE`; the UI pass uses it for `UIVertex.texture`, and images referenced this way get no automatic barrier: register them on the pass with `BindingOutput::{sampled_read, storage_read, storage_write, buffer_read, buffer_write}`, which append an access. `lava`, `core` and lava's GPU tests enable `generic_const_exprs` because every draw method returns a `RasterBuilder` one draw larger (`[Draw; N + 1]`). Slang numbers fragment outputs from location 0 whatever their `SV_Target` index, so a pass that writes attachments other than the first gives them `[[vk::location(n)]]`. Every pass is its own SPIR-V module, so passes can share entry points from an include (the scene passes' `scene_mesh`). A generated push-constant struct gets Slang's alignment (`repr(C, align)`), so its tail padding matches.
- Specialization constants are baked into the pipeline, for values that are the same on every run (sizes, modes, a bindless handle that is fixed for the app's lifetime, like the font atlas's). Never put buffer addresses in them: an address differs from run to run, so Mesa's shader cache never hits and every start compiles the pipelines again (0.7 to 1.2 s here, against 0.1 ms cached), while the baked addresses gained nothing measurable. Declare them with `SCONST(T, name)` (`bindless.slang`; any 8-byte handle type: `Img` aliases, `DynImg`, also `Buf`/`MutBuf`, which lava's test uses) or a plain `[SpecializationConstant] const uint name = 0;`. They become the parameters of the generated `constant_bindings`, in id order, with the same accesses and barriers as push constants. A pass with them keeps its pipelines in a map keyed by the constant bytes (`PassEntry.constants`, at most `MAX_SPECIALIZATION_CONSTANTS_SIZE` < 128 bytes), so every new value builds a pipeline at first use, and a pass reaching 16 pipelines logs a warning: pass values that change on resize or per frame (frame-slot offsets, attachments, settings) as push constants.
- Runtime hot reload: `lava/src/command_buffer.rs` watches `shaders/` and recompiles changed passes. Changing a push-constant or specialization-constant layout still needs `cargo build` so the bindings get regenerated; reloading rebuilds every cached specialization.
- `shaders/compile.sh` → `shaders/bin/` is legacy and isn't used by the build.

## Tests (lava, lava-macros)
- `PATH=$HOME/.cargo/bin:$PATH cargo +nightly test -p lava -p lava-macros`. Add `--no-default-features` to test lava without `profiling`. Narrow with `--lib` (pure unit tests, no GPU), `--test gpu_headless` (real GPU, headless, validation layer on, any validation error fails the test), or `--test gpu_window` (surface/swapchain/present; own `main`, opens a window briefly, skips without a display).
- Pure logic is tested in `#[cfg(test)] mod tests` at the bottom of each module. Never construct a `Buffer`/`Image` or call `Ctx::*` there: `Ctx::get()` blocks forever when lava isn't initialised.
- GPU tests share one context through `lava/tests/common` (`gpu()` guard serialises tests and checks validation errors), so they can reuse the same bindless indices (0, 1, …).
- `core` has GPU-free unit tests (`cargo +nightly test -p core --lib`): the meshlet LOD build, the bake of a small glTF, both scene layouts, material files and slots, the `AssetIndex` layout behind `texture_index`, and the profiler's span capture and reports.
- **Lava's tests never use engine passes.** They render with their own passes in `lava/tests/shaders/*.slang`, compiled only with the `test-passes` feature (enabled by lava's self dev-dependency). With that feature `build.rs` writes the bindings to `$OUT_DIR/bindings.rs` and leaves `src/bindings.rs` alone.
- Golden images live in `lava/tests/golden/*.png`. A mismatch writes `<name>.actual.png`/`.diff.png` to `target/tmp/golden-failures/`. After an intended change to a test shader, re-bless with `LAVA_BLESS=1 cargo +nightly test -p lava --test gpu_headless` and look at the PNGs.
- Slang gives shaders D3D-style `SV_VertexID`/`SV_InstanceID` (without `first_vertex`/`first_instance`).

## Commands
- After changing how meshes or textures are baked, run the `bake` tool with `--force` (see Headless tools).
- **Needs nightly.** `/usr/bin/cargo` (Arch stable) shadows rustup, so use `PATH=$HOME/.cargo/bin:$PATH cargo +nightly check` (or `build`/`run -p game`). Plain `cargo` fails with E0554. The asset paths in `core/src/lib.rs` are absolute (`core::ASSET_DIR` = `game/assets`, the baked files and the asset browser root, and `core::UNBAKED_ASSET_DIR` = `game/unbaked_assets`).
- Slang SDK lives in `lava/slang/` (gitignored). Linking goes through `.cargo/config.toml` (`SLANG_DIR` and rpath). `build.rs` links `slang-compiler` explicitly because `-lslang` would pick up the unrelated S-Lang library.

## Don't read
`target/`, `shaders/bin/`, `*.spv`, `*.glb`, `Cargo.lock`, `vulkaninfo.html`. These are binary, generated, or huge, and the project settings deny them.
