# GameEngine

Vulkan game engine in Rust (edition 2024, uses unstable `#![feature]`s), built on bevy 0.19 ECS **without** bevy's renderer.

## Orientation: read this before exploring
- A **code map** (each file's purpose, key types, and plugins, plus a shader table and live git state) is injected at session start by a `SessionStart` hook. Check it before running `ls`/`rg`.
- Full pub signatures and struct fields live in `.claude/context/api/{lava,lava-build-slang,lava-tests,core,game,lava-macros}.md` (`core.md` also lists the generated pass bindings, from the newest debug build). Read the relevant file instead of grepping for an API.
- These files are generated by the `tools` workspace crate (`tools/`, no `#![feature]`s, so stable cargo works). To refresh them by hand, run `cargo run -q --release -p tools --target-dir target/tools`. It uses its own target dir so it never blocks on the main build lock, and it's cached by mtime.
- **Subagents don't get the hook output.** When delegating exploration, tell the subagent to read `.claude/context/codemap.md` first.
- Known bugs, intended limitations and ideas for future work are listed in `STATE.md`. Check it before debugging or designing, delete an entry when you fix or build it, and add bugs you find but don't fix and ideas worth keeping.
- Every `.rs` file starts with a one-line `//!` doc that feeds the code map. Keep it accurate when a module's role changes, and add one to every new file.

## Crates (dependency order)
- `lava-macros`: proc macros for lava (validation tracing).
- `lava-build-slang`: lava's Slang frontend, called from an application's `build.rs` (see Shader pipeline); compiles its Slang passes and generates their bindings and `PASS_MAP`. Its `slang/` (`bindless.slang`, `profile.slang`, `ray_tracing.slang`, searched by every session) is the Slang side of lava's shader contract (the "Shader contract" section of lava's `lib.rs` docs: descriptor sets, push constants, clock regions, handle and instance layouts). With its `hot-reload` feature (only as a normal dependency; the build script's copy never compiles lava) it also holds the runtime shader hot reload. The only crate that links Slang; lava has no Slang in any feature combination, so a frontend for another language (`lava-build-glsl`, see STATE.md) could sit beside it.
- `lava`: Vulkan abstraction over `ash` + `gpu-allocator`; it takes SPIR-V and has no Slang. Global `Ctx` state, bindless descriptors (`BindlessHandle`; lava keeps no index bookkeeping, see Bindless slots), `lava::init(Option<display>, validation, gpu_assisted, &PASS_MAP)` (`None` = headless; the application's pass map, see Shader pipeline), per-window `Surface` + `Swapchain` objects, usage-typed `Buffer`/`BufferSlice` and `Image`/`ImageView` (a `BufferSlice` is only what the GPU sees, an address, a size and the usage, borrowing its buffer; every command takes it as a `VkDeviceAddressRangeKHR`, so lava requires `VK_KHR_device_address_commands` and never passes a buffer handle or offset, and the flags each command takes come from the usage (`address_flags`: storage known or unknown, always fully bound); host access is `Buffer::host()`/`host_mut()`, plain `&[T]`/`&mut [T]` over the mapping, so sub-ranges and copies are std's and the borrow checker rules out aliasing, plus `host_ptr()` for buffers whose elements are owned one at a time through a shared reference (core's material slots, the clock counters), whose derefs are `unsafe` with the invariant stated at the call site; host writes racing GPU reads of a frame in flight stay a convention, the `frame_in_flight * MAX` rings) (type-state generics `F: Format`, `U: *Usage`, and for images `D: Dim` (`image/dim.rs`: `D2`, the default, or `D3`; extents and offsets are `D::Extent`/`D::Offset`, `UVec2`/`IVec2` or `UVec3`/`IVec3`) and `V: Views`: the default `Single` keeps one view, handle and tracked layout for all mips (render targets, textures), `PerMip` (`MipChain<F, U, D>`) adds a view, handle and layout per mip (`mip_view(level)`, `bind_mips_sampled/storage(first)` put mip `i` at `first + i`) for images whose mips the GPU accesses one at a time; `extent()`, `mip_levels()` and `handle()` are methods; commands only take `ImageView<F, U, D>`, which knows its mip range and the extent of its first mip, so `view.whole()` is that mip's `ImageSlice`; transfers work in any dimension, attachments and presenting take 2D views, and lava-build-slang gives each generated image parameter the dimension of its Slang `Img` shape (`Tex3D` needs a `D3` view); an image gets exactly its usage's flags, one marker type per combination Vulkan allows, generated by `usages!` in `image/usage.rs` and named by concatenating `ColorAttachment`/`DepthAttachment`, `Sampled`, `Storage`, `HostCopy`, `TransferSrc`, `TransferDst` in that order, e.g. `ColorAttachmentStorageTransferDst`; clears, copies and blits need `IsTransferSrc`/`IsTransferDst`; buffer usages are generated the same way in `buffer/usage.rs` from storage, uniform, vertex, index and indirect, and every buffer also gets device address and transfer src/dst, because leaving transfer out made no measurable difference, and acceleration structure build input when that feature is on (no measurable difference in the benchmark view either); besides these static types, `format::Dynamic(VkFormat)`, `image::usage::Dynamic(ImageUsageFlags)` and `buffer::usage::Dynamic(BufferUsageFlags)` are values known only at runtime that meet every bound: images and buffers store their `F`/`U` values, and every command buffer function and generated binding calls `aspect_check`/`texel_check`/`usage_check` with what its bounds require, which is empty for the `StaticFormat`/`StaticUsage` types and panics for a dynamic one that lacks it; clear values are lava's `format::ClearValue` (a `Dynamic` format takes one directly and checks its variant); `new`/`with_mip_levels` are for static types, `Image::with_params(format, usage, ..)`/`Buffer::with_usage(usage, ..)` take any, and `erase()` turns an image into a `DynamicImage<D, V>` (`Image<format::Dynamic, usage::Dynamic, D, V>`) and a buffer into a `DynamicBuffer` (`Buffer<u8, usage::Dynamic>`); the swapchain's images and core's viewport target have its runtime `format::Dynamic` (`Swapchain.format`), and `GpuTexture` is an `Image<format::Dynamic, SampledHostCopy>`), `CommandBuffer` with automatic barrier tracking (every image access asks for `GENERAL`, except attachments, which are in `ATTACHMENT_OPTIMAL` while drawn to; a pending write gets no second barrier for stages and accesses an earlier barrier already made it visible to, and a layout transition waits only for its image's tracked accesses, or for everything when there are none; each queue keeps the pending accesses of what was submitted to it (`FamilyQueues.pending`, locked while a command buffer for it is recorded and submitted, so leases sharing a queue record one after the other; `reselect` copies them to the new queue), and destroying an image or buffer forgets its accesses on every queue; an image's tracked layout is an atomic in the image (one per mip for a `MipChain`, one per image of a swapchain; a transition gets one barrier per run of neighbouring mips with the same old layout, and memory dependencies stay per image in the global memory barrier) that moves when an access is *recorded*, so bindings may be recorded in any order or dropped, but command buffers that share an image must be recorded one after the other and submitted in that order), and `compute`/`raytrace`/`raster` dispatch. A `Queue<Q>` is a lease on one queue of a family (`FamilyQueues` in `vkobjects/queue.rs`): `Queue::new()` takes one no other lease holds while there is one, then the least shared one, which leases take turns on (a `Mutex` per queue). `is_optimal()`/`reselect()` move a lease off a shared queue once another freed up (rare; it waits for the old queue to idle, so its slots stay valid). A frame loop submits its `FrameSlot`s through one lease, so its frames stay in order; core keeps its lease with its slots in the `FrameSlots` resource. A `SemaphoreInfo` (`Semaphore::info()`) is waited on at `ALL_COMMANDS` unless `.at(Stage::{Compute, RayTracing, Raster, Transfer})` names the kind of lava command that first touches what it guards, a hint the caller is responsible for: core waits for its swapchain image at the composite pass (`Compute`) when the scene is drawn straight into it, else at the UI rendering (`Raster`), so the frame culls and shades before the image is acquired; the transition out of `PRESENT_SRC_KHR` waits at `ALL_COMMANDS`, which chains with any wait stage. Every submission ends with a barrier that makes its writes host-visible (readbacks, clock counters). Host image copies (`Image::copy_from`) aren't synchronised with frames in flight. A generated `Pass::push_bindings(...)` returns a `BindingOutput<K>` (push constants, specialization constants and accesses; a pass with specialization constants returns an `IncompletePass` that `.constant_bindings(...)` completes; the zero-sized `kind::{Compute, RayTracing, RasterVertex, RasterMesh}` marker decides where it can be recorded). `cmd.raster(extent)` starts one rendering: `color_attachment(view, clear)` calls (only before the first draw), `depth_attachment(view, clear)`, then any number of `draw`/`draw_indexed`/`draw_indirect(_count)`/`launch(_indirect)` calls, each with its own `RasterState<COLOR_ATTACHMENTS>` (`blends([..])`, an array of one `Blend::{Replace, Alpha, Add, Attenuate, Skip}` per colour attachment, default all `Replace`; `depth_write`; `backface_culling`; `wire_frame`), and `record(name)` records them in one rendering under one GPU scope. Within a rendering, depth and blending follow draw order without barriers, but nothing else does, so no draw may read what an earlier one writes. `RasterBuilder<'a, DRAWS, COLOR_ATTACHMENTS>` counts both in its type (each call returns a builder one larger), so a draw with the wrong number of blends doesn't compile, and a draw that may not happen is recorded with a count of 0 (direct draws of 0 instances are skipped).
- Traits only lava implements (`Format`, `ImageUsage`, `BufferUsage`, `Dim`, `Views`, the aspect markers, `SemaphoreType`, `QueueFamilie`, `Level`, `IndexFormat`) have the supertrait `crate::sealed::Sealed`, a public trait in a private module: other crates can bound by them but not implement them, and their sub-traits (`IsSampled`, `HasTexels`, ...) are sealed through them. Seal new ones the same way; `VertexPosition` stays open for vertex types of other crates.
- Epochs (`lava/src/epoch.rs`): views, slices and `SemaphoreInfo`s borrow what they name (`Copy`, no count), and lava counts nothing per use. A frame reserves an `Epoch` (`epoch::reserve()`) before it reads anything its GPU work reaches, through commands, addresses or bindless slots, and hands it to `FrameSlot::begin(epoch)`; the slot completes it once the frame's fence signalled (at its next `begin` or drop), or right away if the frame failed before it was submitted. Core reserves it in the render sub-app's `extract`, before `ExtractSchedule` (`FrameEpoch`, taken by `render`), and the headless renderer before its extract. Dropping an image, buffer, semaphore, swapchain, surface or acceleration structure queues its destructor stamped with `epoch::latest()`; destructors run in drop order once every epoch up to their stamp completed, never right away, so replaced resources are just dropped. What a present may use (semaphores, swapchains, surfaces) waits for one epoch more, since a present has no fence. `lava::wait_idle` completes every submitted epoch and runs what that frees (call it outside `Frame::execute`: destroying an image locks the queues' pending accesses). Slots the GPU reads by index follow the same rule by hand: core's material free list stamps a freed slot with `epoch::latest()` and reuses it once `epoch::completed()` reached that.
- Ray tracing (`vkobjects/acceleration_structure.rs`, `vkobjects/rt_pipeline.rs`): three features, `acceleration_structure`, and `ray_query` and `ray_tracing_pipeline` on top of it (each only where the device has it; a pass whose SPIR-V uses ray queries, `PassEntry.ray_query`, or a ray tracing pass gets no module or pipeline without its feature and panics when recorded). `Blas`/`Tlas` (`AccelerationStructure<Bottom/Top>`) own their memory (`create_acceleration_structure2` from an address range) and know their device address (not their buffer's) and scratch sizes (multiples of `scratch_alignment()`, so one scratch slice serves a batch). A BLAS is built from `BlasGeometry::Triangles` (`Triangles::new`/`indexed`, any `VertexPosition`, u16/u32 indices, optional transform, `opaque`) or `::Aabbs`, a TLAS from `Instances` of `Instance` (lava's mirror of `VkAccelerationStructureInstanceKHR`, which passes can write too). `cmd.build`/`cmd.update` (refit, `BuildFlags::allow_update`) record one `vkCmdBuildAccelerationStructuresKHR` per call; compaction is `cmd.query_compacted_sizes` into `CompactedSizes` (polled on the host, never waits), `compacted(size)` and `cmd.compact`. Barriers: a structure's memory is its buffer's range, and every acceleration structure command runs at the build stage; a TLAS build or a trace also reads `EVERY_ACCELERATION_STRUCTURE` (the BLASes lava can't list), an empty range that only conflicts with acceleration structure writes. Trace reads add `MEMORY_READ`, because Mesa's ANV otherwise lets a trace after an in-submission rebuild see stale nodes (`TRACE_READ`). `cmd.raytrace(bindings, [w, h, d])`/`raytrace_indirect` dispatch ray tracing passes.
- `lava-tests` (`publish = false`): lava's GPU tests as an ordinary lava user, with their own passes (see Tests).
- `core`: engine library made of bevy plugins wired in `core/src/lib.rs::CorePlugin`. It covers assets (the scene/material/mesh/texture files, their loaders, and the `bake` tool in `core/src/bin` that makes them from glTF), the render sub-app (pipelined, `ExtractSchedule`), a custom immediate-mode UI with docking, the editor (gizmos, picking, console, asset browser), the profiler, physics (BVH raycasts), and the scene.
- `game`: the game binary (spawns a camera) plus the headless `render` tool in `game/src/bin` (see Headless tools).
- `tools`: dev tool that generates the Claude Code context (code map + API files) from the sources.

## Coordinates
- World space is left-handed with +Z up, +X forward and +Y right (Unreal's convention). A camera looks along its local +X; `update_camera` (`scene/camera.rs`) turns that into Vulkan's view space (+Y down) and uses a reversed-depth `perspective_lh`, and `ray_direction` inverts exactly that. Don't use bevy's `forward()`/`up()`/`right()`/`looking_at`, which assume -Z forward and +Y up; rotate `Vec3::X`/`Y`/`Z` instead.
- The bake converts glTF (right-handed, +Y up) by swapping Y and Z in positions, normals and node transforms, and flips the triangle winding, so front faces are clockwise on screen (lava's `FrontFace::CLOCKWISE`). Changing this needs a bake with `--force`. A mirrored instance (a world transform with a negative determinant) is handled by `scene_mesh` in `scene_raster.slang`: it swaps each triangle's winding back, and normals are transformed by the cofactor matrix (the inverse transpose, so non-uniform scale keeps them perpendicular) with the determinant's sign.

## Viewport
- With the editor, the scene is rendered into an offscreen image in the swapchain format (`ViewPortTarget` in `core/src/render/render.rs`) that starts at the initial window size and only grows; the scene uses its top-left `rect.size()` pixels, the passes get that size as an argument, and the tab draws it with matching UVs (`ViewPort.image_size`). `extract_view_port` writes its bindless handle into the main world's `ViewPort`, and the tab (`editor/viewport.rs`) draws it as a UI image. `ViewPort.rect` is the tab's content area; `hovered`/`focused` gate picking, drops and camera input. `paused` (the "Pause Viewport" button in Render Settings) makes `record_frame` skip the scene passes; the tab keeps showing the last image.
- Without `EditorPlugin` there is no `ViewPort`, and the same passes draw straight into the swapchain image. The scene is drawn from the first `Camera` (`extract_camera`, a warning once with several); without one only the UI is drawn.
- An empty `DockingNode` leaf (`window: u32::MAX`) is just free space; a window dropped on it fills it.
- Since bevy 0.19 resources are entities: the Hierarchy tab lists them by type name (`IsResource`), the Selected tab edits the reflected ones like any component, and the Delete key skips them. To make a resource editable, derive `Reflect` with `#[reflect(Resource)]` (auto-registered); a field that can't be reflected needs `#[reflect(ignore, clone)]`, because the tab works on a `reflect_clone` of the value every frame.
- UI windows have no open/close calls: `ui.build(label, …)` requests a missing tab (created next `PreUpdate`), and `update_windows` closes every tab that wasn't built during the previous frame. `windows.ron` is only layout memory: a saved window (rect, tab group, dock slot) is created when one of its tabs is first requested, and dock slots nobody requested in the first frame are pruned. A reopened tab returns to its last rect; on exit only open windows are saved.

## Headless tools (use these to check your work)
- **Render to a PNG:** `PATH=$HOME/.cargo/bin:$PATH cargo +nightly run -q -p game --bin render -- game/assets/sponza.scene.ron /tmp/out.png`, then Read the PNG. It takes any scene file inside `game/assets` (`.scene` or `.scene.ron`; to render several scenes together, write a `.scene.ron` of `SpawnScene` entities) and draws it at `--size WxH` (default 1280x720) under the game's sky from a camera at `--eye X,Y,Z` looking at `--target X,Y,Z` with a vertical `--fov DEG` (default: from 0,0,2 towards 10,0,3, 65°), once the scene, everything it references and the sky are loaded. Takes about 2 s for sponza. Write the PNG outside `target/`, which is denied for reading. `--frames N` renders N frames (the PNG is the last), `--profile DIR` profiles them (see Profiling) and prints the summary.
- It uses `HeadlessRenderPlugin { size }` (`core/src/render/headless.rs`), which only initialises lava: no window, swapchain, UI, console or render sub-app. Once the scene is loaded, `render_frame(main_world, &settings)` runs the extract systems on a render world it keeps (with its queue, frame slot, pending accesses, target and readback buffer) in the main world, draws the scene passes (`record_scene` in `render.rs`, shared with the windowed frame) into an RGBA8 image and copies it into the readback buffer; `read_pixels(world)` returns the last frame's pixels (reading that host-visible buffer takes about 10 ms, so it isn't done per frame).
- **Bake assets:** `PATH=$HOME/.cargo/bin:$PATH cargo +nightly run -q --release -p core --bin bake -- [--force] [FILE...]` turns every `.glb`/`.gltf` in `game/unbaked_assets` (`core::UNBAKED_ASSET_DIR`) that is newer than its baked scene into files in `game/assets`, and every `.exr` into a `.tex` of the same name. It uses no bevy app and no GPU (sponza: about 50 s, 2.3 GiB peak memory, 462 MB baked). The meshlet build is not deterministic, so a rebake changes the mesh files (and a few pixels).
- **Bake assets** writes binary files; add `--ron` to also write `.scene.ron` and `.mat.ron` next to them for reading. The render tool loads either layout.

## Profiling
- Everything below is the `profiling` cargo feature (lava's only feature; default on in `lava`, `core` and `game`; `core` and `game` depend on the crate below without default features). Without it (`cargo run -p game --no-default-features --features dynamic_linking,hot-reload`) there is no `core::profiler` module, no `ProfileLayer`, `FrameSlot::set_timestamps`/`set_counters` do nothing, neither `VK_KHR_shader_clock` nor `VK_KHR_performance_query` is enabled, and lava-build-slang's Slang session (`lava-build-slang/src/compile.rs`, told by lava's build script through `links = "lava"` metadata, `DEP_LAVA_PROFILING`) leaves out the `PROFILING` macro; `lava::init` asserts the pass map was compiled for the same setting, so `CLOCK_REGION(...)` compiles to nothing. Gate new profiler code with `#[cfg(feature = "profiling")]`. With every switch off, the profiler cost about 0.04 ms wall per frame over leaving it out.
- `ProfilerPlugin` (`core/src/profiler`) keeps the times of the last `MAX_FRAMES` in `Profiler.times` (wall and GPU); a frame is the time between two runs of `end_frame` (`Last`), numbered by `profiler::frame()` and timed by `profiler::now_ns()`. Four independent systems record into it, each with its own switch (`Profiler::{spans, timestamps, counters, clocks}`, the tab's checkboxes, the `ProfilerPlugin` fields), its own lava or core API and its own ring tagged with the frame number: CPU spans, GPU timestamps, pass queries (pipeline statistics and hardware counters) and shader clocks. A switch that is off just records nothing new. The game adds the plugin in `main.rs`; the editor's "Profiler" tab needs it. There is no CPU time: the frame time is wall time, waiting included, and the selected frame's timeline shows what each thread did and where it waited.
- CPU spans (`profiler/spans.rs`): `spans::ProfileLayer` writes every span entered on any thread, when it ends, into that thread's fixed ring (`SPANS_PER_THREAD`, a `head` atomic, no lock; old spans are overwritten; an `Arc` the thread owns, so it dies with the thread), as a `SpanKind`: bevy's "system" (systems and run conditions) and "schedule" spans are named by their `name` field, any other span by its name plus its `name`/`pass` fields (e.g. `system_commands <system>`, `compute BvhCull`); a span without such fields keeps its static name, others are interned through a per-thread cache. A span belongs to the frame it started in (`CpuSpan.frame`). The rings are read only while recording is off (paused): `spans::for_each_thread` skips the slots the at most `MAX_DEPTH` spans still open at the pause can overwrite. There is no live profile: `Profiler::select(i)` (a click in the tab's graphs) pauses and scans every ring once to build the one `Profiler.selected` `FrameProfile` (spans per thread, GPU scopes, pass queries, shader clock regions); `save` builds all of them once.
- `core::register_tracing()` installs the subscriber (console, stderr and profiler layers); the game calls it first in `main`, because bevy creates a system's span when the system is added and a span created before the subscriber exists never records. `ConsolePlugin` calls it if `main` didn't. The `render` tool installs its own subscriber with `ProfileLayer`. The console layer sends each event through a bounded channel (`MAX_ENTRIES`, events past that are dropped from the console only); `console_window` drains it into `ConsoleLog`, which owns the entries, numbered by arrival, and filters them (level, substring) incrementally into `ConsoleUiState.matches`.
- `bvh_cull.slang`'s node queue (`bvh_node_stack`, `~0` = empty) and meshlet batch counters (`meshlet_batches`, 0) are filled once (`RenderResources.fresh`, set again when the attachments or the cull buffers grow): it writes every slot and counter it consumes back to that value. `candidate_meshlets` is never filled; only published batches are read. Values other groups write (queue slots, `node_count`, the batch counters) are polled with atomics, and a group only processes partial batches once `node_count` is 0, when nothing can be appended any more. What the pass drops for lack of space (nodes, candidates, a draw's meshlets) sets a bit of `TraversalVariables.overflow`; the cull buffers start at `CULL_BUFFER` entries (64k, `meshlet_batches` at a 64th of the candidates) and `RenderResources::fit` doubles an overflowed one (read from the host like `visible_meshlets`, a frame late; that frame drew without what didn't fit) up to `MAX_CULL_BUFFER` (2M), where it warns once. On this iGPU (Intel Arc B390, shared LPDDR5X) every MB a pass writes costs about 7 µs, so avoid per-frame fills and clears of big resources.
- **Benchmark view** (the worst case found in sponza, about 10k meshlets drawn): measure performance changes with it, in release builds, comparing frame, GPU and per-pass times against a run of the old build:
  `PATH=$HOME/.cargo/bin:$PATH cargo +nightly run -q --release -p game --bin render -- game/assets/sponza.scene.ron /tmp/bench.png --eye -12.44,-0.21,2.61 --target -3.31,-0.21,6.69 --fov 64.7 --size 2560x1440 --frames 120 --profile /tmp/bench`. After a shader change, the first run compiles every pipeline into Mesa's cache (its first frame then takes several hundred ms), so run it twice and judge frame times by the median.
- The B390's clock moves between 900 and 2500 MHz from run to run and within a run (`act_freq` in `/sys/class/drm/card0/device/tile0/gt0/freq0/`), and the same frame takes about 2.5 times as long at 900. Compare GPU times only at the same clock: alternate the variants' runs and compare the per-pass "AVG GPU Core Frequency" counter (in the default set) or read `act_freq`.
- GPU timestamps (`lava::profiling::timestamps`): a `FrameSlot` with `set_timestamps(true)` times every compute and ray tracing pass (named by its generated struct), every rendering (named by `record(name)`: "Scene", "Outline", "UI", "Gizmos") and every `cmd.begin_scope(name)`/`end_scope()` group (also debug labels), under a root scope "frame". The `GpuScope`s come back in `Frame::last_timestamps()` when the slot is begun again, relative to the root scope, and `Frame::last_timestamps_start()` says when that started on the host's clock (`VK_KHR_calibrated_timestamps`, `Features::calibrated_timestamps`, only with `profiling`; `None` without it, and core then uses the submit time, taken right after the submission). That is `FrameProfile.gpu_start_ns`, which places the GPU lane of the timeline and the Chrome trace.
- Pass queries (`lava::profiling::counters`): `FrameSlot::set_counters(Some(selection))` gives every pass and rendering a pipeline statistics query (task/mesh/fragment/compute invocations; clipping counts aren't allowed while mesh shaders draw) and a hardware counter query (`VK_KHR_performance_query`) for the selection; `None` records none, and `Frame::last_counters()` returns the `PassCounters`. The slot rebuilds its pools when it gets a selection that isn't `Arc::ptr_eq` to its own. `counters()` lists the graphics family's counters (270 on the B390 with Mesa's ANV; `/proc/sys/dev/xe/observation_paranoid` must be 0, which it is here). A selection holds at most `MAX_COUNTERS` (8) and must fit one pass, since a frame can't be submitted once per pass (`Profiler::set_counters` refuses others, a slot fails to begin with one). A pass's values land in `PassResult.values` in the order of `PassCounters.counters`; the reports sum amounts per frame and average rates (`CounterUnit::is_rate`) over the pass's queries. The pools hold the profiling lock (acquired for the first, released with the last; another process holding it disables counters with a warning) and are reset on the host, since a command buffer may not reset a counter pool it begins queries of. `ProfilerPlugin.counters` names the start selection (`DEFAULT_COUNTERS`: frequency, XVE active/stall/occupancy and ALU0 instructions, L1 bytes read/written and hits, which fit one pass on the B390; ANV reads 0 per pass for GPU Busy, GPU Memory Byte Read/Write and L3 Read/Miss there, so check a counter on its own before trusting a 0), the Profiler tab's "Performance counters" list changes it (counters that wouldn't fit are dimmed), `render --counters A,B` replaces it and `none` turns pass queries off. The queries cost the benchmark view about 0.4 ms of 4.4 (BvhCull and Scene the most), so compare times with `--counters none`.
- Shader clock regions (a debugging aid): `CLOCK_REGION("name")` at the start of a block (`lava-build-slang/slang/profile.slang`) adds each subgroup's `VK_KHR_shader_clock` ticks until the block ends, plus one subgroup packed above `CLOCK_TICK_BITS`, with a single atomic to one of 64 striped counters in descriptor set 2 (`lava::profiling::clock`, one cache line per stripe), per pass (`PROFILE_PASS`, which the Slang session defines per pass) and region. It only counts in a pass that `#define USE_CLOCKS` before its first include of `profile.slang`, elsewhere it is empty, so shared code can keep regions; `composite.slang` has a "test" region. Region names come from Slang's reflection of the hashed strings (`PassEntry.regions`), at most 8 per pass. `USE_CLOCKS` declares the specialization constants 901 to 908 (`profiling::clock::CLOCK_REGION_IDS`, copied in lava-build-slang, also without `profiling`, so the API doesn't change with the feature); lava-build-slang reflects them like the pass's own but bakes the name hashes into its `constant_bindings` instead of taking them as parameters, so a clocked pass needs `.constant_bindings()`, possibly with no arguments. They are the switch: `clock::set_enabled` (the profiler's `clocks`) makes `constant_bindings` bake the hashes, off it bakes 0s and the driver folds the regions away; each state is its own pipeline. Adding or renaming a region needs `cargo build`: a hot-reloaded region with a new name doesn't count until then. The L2 serialises the atomics to a cache line (about 200 cycles each on the B390), so a full-screen pass of 30k subgroups pays about 0.1 ms per atomic per subgroup; two of them were the biggest part of the tonemap's (now `composite.slang`'s) time, so put regions where they matter, not everywhere. Counters only grow and wrap; `clock::read` reports the difference since the last read as `RegionTime`s, so nothing waits, and `end_frame` reads them once per frame into the frame that reads them. Every submission ends with a barrier that makes the counters host-visible. The ticks are about core clock cycles and summed over parallel subgroups, so the report shows each region's share rather than ms. Fragment shaders stay out: a buffer write disables early depth testing (it raised Raster's fragment invocations by 30%). Without `shaderSubgroupClock`, clocked pipelines can't be created. The windowed `render()` sets its slots' timestamp and pass query switches from the render world's `GpuTimings` and keeps their results per frame slot (reusing their buffers), which `extract_gpu_timings` hands to `Profiler::add_timestamps`/`add_counters`; they join the frame that ran when they were submitted, a few frames later. GPU memory comes from `lava::profiling::memory_report()`.
- Output: the editor's Profiler tab shows the four switches and live frame and GPU graphs; the selected frame gets a timeline and its GPU scope, pass query, clock region and CPU span tables (filterable by kind). `Profiler::save(dir)` writes `profile.txt` (frame and GPU times, GPU scopes, pass queries, clock regions, top 25 CPU spans, memory) and `profile.json` (Chrome trace for Perfetto). The tab's "Save capture" writes to `profiles/<unix time>/`, `GAME_PROFILE=DIR[:FRAMES] cargo run -p game` saves the first FRAMES frames (default 300), and `render --frames N --profile DIR` the headless frames.

## Performance conventions
- No heap allocation per frame at steady state: reuse buffers (`clear`, `clone_from`, fixed-capacity rings, scratch `String`s), allocate once up front.
- Data shared between threads on a hot path is synchronised with atomics where they can express it; a mutex is fine where they can't, or off the hot path.
- Expensive derived data (profiles, reports, tables) is computed on demand, once, and kept until its input changes; nothing is rebuilt every frame just to be displayed.
- Render targets are bound by bandwidth too: use the smallest format whose tonemapped result stays within about 2 levels (`accum` RGBA16F and `revealage` R8 instead of RGBA32F/R16F, with a B10G11R11 HDR target, took the benchmark view's tonemap from 0.80 to 0.62 ms at 900 MHz, and a blended close-up's Scene from 3.47 to 2.82 ms). Compare the new images' signed per-channel difference against the old: a format that truncates (B10G11R11 does) shows up as a one-sided bias. The 16-byte G-buffer that replaced that 4-byte HDR target cost the benchmark view 0.35 ms at 900 MHz (composite +0.3 ms) and 0.9 ms at 2500 MHz (Scene +0.55, composite +0.35), with one directional light.
- Only images the host writes get host transfer usage: `Image::copy_from`/`copy_region_from` need an `IsHostCopy` usage and `Features::host_image_copy` (`VK_EXT_host_image_copy` on a device with host-visible device memory, `rebar`; without it the flag is left off the image and the copy fails) (textures, the font atlas and the browser previews use `SampledHostCopy`). Dropping the implicit transfer usages from every image made no measurable difference. Giving it to every image, render targets included, made the benchmark view's GPU time 4.06 instead of 3.34 ms (Scene 2.93 instead of 2.44, composite 0.84 instead of 0.65, at about 800 MHz), presumably because ANV then can't compress them.
- Full-screen compute passes are bound by memory, not arithmetic: keep the default 8x8 workgroup (Intel's tiled layouts hold a 2D block of texels per cache line, so a subgroup covering a 32-pixel row cost 20% more than an 8x4 tile), and several pixels per lane or hoisting the loads above the branches gained nothing once the profiler's atomic was down to one per subgroup.

## Bindless slots
- Lava never picks a descriptor index: `Image::new`/`with_mip_levels`/`with_params` make an unbound image (null `handle`), and the builder calls `bind_sampled(index)`/`bind_storage(index)` (gated by `IsSampled`/`IsStorage`) bind it right away and return it, e.g. `Image::new(extent)?.bind_sampled(a).bind_storage(b)` for an image in both sets. Both go through `bindless::bind(images, handles)`, which writes each image view into the slots of the handle at the same position (`BindlessHandle::sampled(i)`/`storage(i)` name one set), checks the usage, and makes one `vkUpdateDescriptorSets`; it sets no handle on the image. The texture slots use it to write many slots at once. A `Swapchain` never binds its images, also not after `recreate`: `bind_storage(indices)` puts image `i` at the `i`-th index. `resize_swapchain` binds the new images at new slots after every recreation (the image count can change: Mailbox gets one more image here) and gives them new `render_finished` semaphores; the old swapchain's slots come back through the drop hook once it is destroyed. `Swapchain::recreate` hands back the old swapchain, which core drops right away with its `render_finished` semaphores (the new swapchain gets new ones): they are destroyed once the frames and presents that may use them are done (Epochs), so a resize stalls nothing. Core's `Swapchain` resource waits for the device (`lava::wait_idle`) when dropped. A window without an extent (a zero window size, or `Surface::is_minimised` after a failed recreation) sets `Swapchain.minimized`, and `render` skips the frame; an out-of-date acquire recreates in place, or skips the frame when the window was minimised since the extract. `RenderPlugin { min_frame_time, min_frame_time_minimized }` is the least time between frames (`FrameLimit`, slept before each): unlimited and 50 ms (20 fps) by default. Both sets are `UPDATE_UNUSED_WHILE_PENDING`; dropping an image leaves its descriptor stale. Set 2 holds only the profiler's shader clock counters.
- `lava::bindless::on_drop(hook)` sets a global function called with every bound handle whose view is destroyed: each handle of a destroyed `Image` that isn't null (the whole view's, then each mip's) and of a destroyed `Swapchain`'s images, once every frame that may reach it is done (Epochs). Core sets the hook in `bindless::init()` (right after `lava::init`) and gets its slots one at a time from `bindless::sampled_slot()`/`storage_slot()` (atomic counter plus free list per set), which the hook refills. So a replaced depth attachment or viewport target never frees a slot a pending frame reads.
- Textures sit at `TEXTURE_SLOTS_BASE + asset index` (`texture_index` in `assets/texture.rs`), known as soon as the handle exists. `write_texture_slots` (in `Last`) fills every texture slot with a white placeholder on its first run, then follows `AssetEvent<GpuTexture>`: a loaded or reloaded texture is written into its slot, a removed one is replaced by the placeholder. `scene_raster.slang` skips normal mapping when the normal sample is exactly (1, 1), which is the placeholder.

## Asset files and the asset browser
- There is no bevy asset processor and no `.meta` file: `asset_plugin()` loads `game/assets` unprocessed. The `bake` tool (`assets/bake.rs`) turns the default scene of `sponza.glb` into `sponza.scene` plus `sponza/{meshes,materials,textures}/<name>.{mesh,mat,tex}`, so every file loads on its own. A bake deletes and rewrites the scene's whole directory.
- The files have no magic or version: after changing a layout (or the `Material` struct), bake with `--force`. Binary files are written with the `write_slice`/`write_compressed` helpers in `assets/util.rs` and read back front to back through bevy's async `Reader` (`read_slice`/`read_compressed`); big payloads are zstd-compressed, structured ones are `postcard`.
- Scenes (`scene/file.rs`) store entities: a parent per entity (`u32::MAX` = the spawn root), the referenced asset paths (relative to the scene file; a leading `/` means the asset root), and one column per component type, named by `short_type_path`. `.scene` frames the head and then one postcard frame per column; `.scene.ron` lists the same data entity by entity. Handles are saved as indices into the assets, and loads start with `load_context.load` (deferred), so the scene is loaded right after its file is read. The bake writes the `Instance` column first.
- A component is saved if it implements `SceneComponent` (automatic for `Component + Clone + serde`; `Instance` does it by hand through `SaveCtx`/`LoadCtx`) and is registered with `ReflectSceneComponent` (`#[reflect(SceneComponent)]`, or `register_type_data` like `Transform`/`Name` in `ScenePlugin`). An unknown or ambiguous column name fails the load.
- Spawning: `SpawnScene { scene }` on an entity makes the exclusive `spawn_scenes` create the scene's entities as its descendants, then removes the component. It requires `Transform` and is a scene component itself (saved as an asset index), so a scene can place other scenes. The Hierarchy tab saves the selected entity's descendants to the typed path (relative to `ASSET_DIR`, `.ron` picks RON); materials without a file are written to `<scene>/materials/material_<n>.mat` first.
- The bake keeps the glTF node tree (local TRS, names, empty nodes); a mesh with several primitives gets one child entity per primitive. Lights, cameras, skins, morph targets, animations, non-triangle primitives, extra UV sets, texture transforms, GPU instancing and other scenes are dropped with a warning.
- `.mesh`: `MeshHeader`, the compressed GPU data, the compressed collision BVH. `.tex`: `TextureHeader`, a `PREVIEW_SIZE` RGBA8 preview, then one compressed mip after the other. Textures are BC7 (`TextureKind::Color` sRGB, `Data` linear) or BC5 (`Normal`, the shader reconstructs z), chosen by the material slot that uses the image. An OpenEXR file becomes BC6H (`Hdr`, unsigned half floats, no alpha); its preview is clamped to 1.
- The sky is the `Skybox` resource (`scene/mod.rs`), a `Handle<GpuTexture>` to an equirectangular texture (Z up, +X at u = 0.5 with u growing towards +Y, v = 0 at the top), editable in the Selected tab. `extract_skybox` hands its texture slot to `composite.slang`, or `NULL_HANDLE` until it is loaded, which draws a flat colour. The composite pass draws the sky where the depth is still cleared (0), and picks the mip from the angle between neighbouring pixels.
- Opaque surfaces are deferred: the raster pass writes each fragment's material (`material_surface` in `scene_raster.slang`) into `RenderResources.gbuffer` (`R32G32B32A32Uint`, grown with the depth attachment), packed by `GbufferData::pack` (`shaders/include/gbuffer_helpers.slang`, kajiya's code, with its helpers in `packing.slang`): albedo as its square root in 8:8:8 with occlusion added in the spare byte, the world normal in 11:10:11, the square root of roughness and metalness as two f16, emissive as rgb9e5. Blended materials are forward-lit into the `accum`/`revealage` images (see Materials). The raster pass runs even without instances, because it clears the depth. `composite.slang` lights the G-buffer with `light` (`shaders/include/lighting.slang`, shared with the blended pass; its view vector is the pixel's reversed ray), puts the sky where nothing was drawn, composites the blended layers over both and writes the result to the target with `RenderSettings.exposure`, an ACES fit and sRGB encoding, since the targets are UNORM shown as sRGB. There is no HDR image. Outlines and gizmos draw onto the target afterwards, untonemapped: `bvh_cull.slang` also writes the visible meshlets of `OUTLINE` instances into their own list (`OUTLINED_DRAW`), `raster_outline.slang` marks just those in `RenderResources.outline_mask` (an R8 attachment cleared by that rendering, so the scene depth stays intact), and `draw_outline.slang` colours the unmarked pixels within the radius (at most `MAX_OUTLINE_RADIUS`, 8) of marked ones, testing a groupshared copy of its tile plus apron. Gizmos are capped at `MAX_GIZZMOS` (8k) per frame; with more, the Render Settings tab's "First Gizmo" slider picks which are drawn.
- The browser (`editor/asset_browser.rs`) shows the files of `ASSET_DIR` as they are and keeps no per-tile state: only the rows in view are laid out, and a click opens a folder. Kinds match the end of the file name, case-insensitively. A `.tex` tile in view reads just its preview from the file, synchronously, into one main-world atlas image (`Previews`, written by `Image::copy_region_from`); the atlas holds 1024 previews and the least recently shown makes room.
- The browser never polls. A `notify` watcher on `ASSET_DIR` forwards every changed path (access events are ignored): the path's preview is forgotten, and a change directly inside the open directory re-reads it.
- Dragging carries an `AssetDrag` (`ui/dragdrop.rs`), which loads the asset only when a drop target takes it (`drop_in_viewport`, the inspector's handle slots).

## Materials
- A material is its own asset: `.mat` (postcard) or `.mat.ron`, holding `MaterialFile` (factors plus five optional texture paths relative to the file). `MaterialLoader` (`assets/material.rs`) shares one `MaterialState` with the `Materials` resource: a host-mapped buffer of `MAX_MATERIALS`, created on first use, and a free list. Each `GpuMaterial` owns a slot (`gpu` address, `cpu` pointer from `Buffer::host_ptr`, the only way that buffer is accessed) and frees it on drop, for reuse once the frames that may read it are done (Epochs); the renderer writes `material.gpu` per instance (`Buf<Material *>` in `scene_raster.slang`).
- A material's texture indices are final when it loads (`texture_index` of the deferred texture handles), so nothing is written back when a texture arrives, and textures shared by path load once. A mesh dropped from the browser gets a default material from `Materials`.
- `MaterialSettings` exists only on `Selected` instances (systems in `scene/mod.rs`): it is read through `GpuMaterial.cpu` on selection, edits (factors and textures) are written straight back, and it is removed on deselect. Everything sharing the material sees the edit; it is not written back to the `.mat` file.
- `Material` (`shaders/include/datatypes.slang`, mirrored by `MaterialSettings` and `MaterialFile`) needs a bake with `--force` when it changes. `alpha_cutoff` discards fragments with less alpha; a negative cutoff blends instead. Scene meshlets are drawn only with mesh shaders (`VK_EXT_mesh_shader` is required), without a task shader (one was much slower here): `bvh_cull.slang` appends each visible meshlet to a list and counts a stride per `MESHLET_STRIDE` of them in that list's `MeshletDraw` (`TraversalVariables.draws`, indexed by `OPAQUE_DRAW`/`BLENDED_DRAW`/`OUTLINED_DRAW`), which `launch_indirect` takes as the mesh workgroup counts. Workgroup (x, y) draws meshlet x * `MESHLET_STRIDE` + y, so neighbours in the list are drawn apart, which drew fewer hidden fragments. `shaders/include/scene_raster.slang` holds the bindings, the `scene_mesh` entry point every scene pass shares (`mesh_threads` invocations per meshlet, a specialization constant `record_scene` sets to the device's `maxPreferredMeshWorkGroupInvocations`, at most 128; lava's `Ctx::mesh_shader_properties()`), and the material evaluation (`material_surface`, which returns a `GbufferData` and the alpha). Its `MAX_MESHLET_VERTICES`/`TRIANGLES` (128/128) are the limits of `build_meshlets` in `assets/mesh.rs`; changing them needs a bake with `--force`. `wirte_instances` packs each instance's `InstanceFlags` (`OUTLINE`, and `OPAQUE` from the material's cutoff every frame, so editing it switches the instance live) into `InstanceManager.flags`, `INSTANCE_FLAG_BITS` bits per instance; `datatypes.slang` mirrors the bits and reads them with `instance_flags`. `bvh_cull.slang` reads that bit per visible meshlet and writes blended meshlets into their own list (`BLENDED_DRAW`), which `record_scene` draws after the opaque ones, in the same "Scene" rendering (the opaque draw `Skip`s attachments 1 and 2, the blended one attachment 0), with `raster_blended.slang`: weighted blended order-independent transparency (McGuire and Bavoil 2013), so no sorting. Depth-tested without depth writes, it adds weighted premultiplied colour and weight into `accum` (`R16G16B16A16Sfloat`: the weighted colour is clamped below the half-float maximum, because highlights times the weight overflow it; scaling the weight down instead made far layers' colours subnormal and darkened them) and multiplies `revealage` (`R8Unorm`) by `1 - alpha`; both are cleared once (`RenderResources.fresh`), and after that `composite.slang`, which composites them over the lit G-buffer and reads the 8-byte `accum` only where `revealage` < 1 (it is bandwidth-bound; `revealage` is read through the sampler as a `MutTex2D`), resets exactly those pixels, so nothing clears them every frame (a full clear cost more than the rest of the blended pass). The blended pass therefore discards fragments with alpha below 1/255, which couldn't lower the 8-bit revealage and would never be reset. Overlapping layers of very different colour and high alpha mix instead of hiding each other. The importer sets 0 for opaque glTF materials, -1 for blended ones and for masks with a cutoff of 0.

## Shader pipeline
- Source: `shaders/passes/*.slang` (one file = one pass) and `shaders/include/*.slang`, plus lava-build-slang's `slang/`. `shaders/old/` is dead code.
- `core/build.rs` calls `lava_build_slang::Shaders::new().passes(dir).include(dir).define(name, value).optimization(..).compile()` (paths relative to the package, canonicalised). lava-build-slang compiles each pass with `shader-slang` (one session per pass, `lava-build-slang/src/compile.rs`, which its hot reload shares, so both compile alike), writes SPIR-V to `$OUT_DIR/lava/passes/`, and reflects the `[[vk::push_constant]]` struct and the specialization constants (`lava-build-slang/src/codegen.rs`) to **generate `$OUT_DIR/lava/bindings.rs`**, rewritten only when it changed. `core/src/bindings.rs` includes it with `lava::include_passes!()`, so the passes are `crate::bindings::*` in core, and `crate::bindings::PASS_MAP` (every `PassEntry`, the SPIR-V always embedded with `include_bytes!`, plus the profiling setting the build used; nothing lava doesn't read) goes to `lava::init`, which lava can't include itself since it is compiled before the application's build script runs. The generated code needs `glam` and `bytemuck` (with `derive`) in the application, uses only lava's public API (`BindingOutput::new`/`with_constants`, `BufferSlice::access`/`address`, `ImageView::access`, `Tlas::trace_accesses`: the API for other binding generators, e.g. GLSL). For example, `raster_ui.slang` → `RasterUi::push_bindings(...).constant_bindings(...)` returns a `BindingOutput<kind::RasterMesh>` that you hand to `cmd.raster(extent)...launch(...).record(name)` (a compute pass's goes to `cmd.compute()`). lava's limits are fixed (`pipeline.rs`): every pass pushes `MAX_PUSH_CONSTANTS_SIZE` (256) bytes, its struct zero-padded (lava-build-slang rejects a bigger struct), at most `MAX_SPECIALIZATION_CONSTANTS_SIZE` (128) bytes of specialization constants, and `MAX_PASS_IMAGES`/`MAX_PASS_BUFFERS` (8/16) accesses inline before they spill to the heap; the pipeline arrays are sized at init from the map. A pass's `PROFILE_PASS` is its index in the map.
- Matrices use column-major layout (`matrix_layout_column` in lava-build-slang's `compile.rs`, shared by the build and hot reload), so a glam `Mat4` arrives untransposed and shaders write `mul(M, v)`.
- Push-constant field types map like this: `Buf<T>`/`MutBuf<T>` → `BufferSlice<T, U: IsStorage>`, and `Img` → `ImageView` (bindless handle, its format bounded by `HasTexels<[T; N]>` of the shader's element type): `Tex2D` reads through the sampler (`IsSampled`), `Image2D`/`MutImage2D` through the storage descriptor (`IsStorage`), and `MutTex2D` reads through the sampler but writes as storage (`UnifiedBinding`, an image bound in both sets). A typed load of a storage image costs several times a sampler fetch on Intel (it was a quarter of the tonemap, now the composite pass), so read an image through the sampler whenever its usage allows. Inside structs behind a `Buf`, `Img` and `DynImg` fields become a `BindlessHandle`. `Accel` (a TLAS's address, `accel.get()` is the `RaytracingAccelerationStructure`) → `&Tlas`, a `u64` inside structs (register it with `BindingOutput::acceleration_structure_read`), never an `SCONST`. Slang structs that mirror a lava type (`MIRRORED_TYPES` in `codegen.rs`: `AccelerationStructureInstance` → `Instance`, whose fields are public for the checks) aren't generated, only layout-checked. `Img` and `DynImg` have `GetDimensions()`. `DynImg` (`bindless.slang`) reads whichever of the sampled/storage index isn't `NULL_HANDLE`; the UI pass uses it for `UIVertex.texture`, and images referenced this way get no automatic barrier: register them on the pass with `BindingOutput::{sampled_read, storage_read, storage_write, buffer_read, buffer_write}`, which append an access. `lava`, `core` and lava's GPU tests enable `generic_const_exprs` because `color_attachment` and every draw method return a `RasterBuilder` one larger (`{ COLOR_ATTACHMENTS + 1 }`, `{ DRAWS + 1 }`). Slang numbers fragment outputs from location 0 whatever their `SV_Target` index, so a pass that writes attachments other than the first gives them `[[vk::location(n)]]`. Every pass is its own SPIR-V module, so passes can share entry points from an include (the scene passes' `scene_mesh`). A generated push-constant struct gets Slang's alignment (`repr(C, align)`), so its tail padding matches.
- A ray tracing pass (`ray_tracing.slang` in lava-build-slang's `slang/`) has one raygen and any number of miss, hit (closest hit, any hit, intersection; procedural with an intersection shader) and callable entry points; `[Group(n)]` puts one at index n of its binding table region (the miss index, an instance's `sbt_offset`, the callable index; 0 without it, dense per region; hit entry points with the same index form one group), `[MaxRecursion(n)]` on the raygen sets the trace depth (1 without it). `compile::ray_tracing_groups` checks them, the pass table bakes them, and `layout_hash` covers them, so a hot reload that regroups is refused. Binding table records hold only handles, no shader record data.
- Specialization constants are baked into the pipeline, for values that are the same on every run (sizes, modes, device limits, a bindless handle that is fixed for the app's lifetime, like the font atlas's). Never put buffer addresses in them: an address differs from run to run, so Mesa's shader cache never hits and every start compiles the pipelines again (0.7 to 1.2 s here, against 0.1 ms cached), while the baked addresses gained nothing measurable. Declare them with `SCONST(T, name)` (`bindless.slang`; any 8-byte handle type: `Img` aliases, `DynImg`, also `Buf`/`MutBuf`, which lava's test uses) or a plain `[SpecializationConstant] const uint name = 0;`. They become the parameters of the generated `constant_bindings`, in id order, with the same accesses and barriers as push constants (ids 901 to 908 are the clock regions', set without parameters, see Shader clock regions). A pass with them keeps its pipelines in a map keyed by the constant bytes (`PassEntry.constants`, at most `MAX_SPECIALIZATION_CONSTANTS_SIZE`, 128 bytes; a key hashes only the pass's own bytes), so every new value builds a pipeline at first use, and a pass reaching 16 pipelines logs a warning: pass values that change on resize or per frame (frame-slot offsets, attachments, settings) as push constants.
- Runtime hot reload is a debugging aid behind the `hot-reload` cargo feature of `core` and `game` (default on), which makes core depend on `lava-build-slang` with its `hot-reload` feature, so keep it simple rather than fast. The build script also writes `$OUT_DIR/lava/hot_reload.rs`, a `hot_reload::Build` (search paths, defines, optimization, watched directories, and per pass in map order its source and layout hash), which lava never sees. `lava_build_slang::watch!()`, which core calls right after `lava::init` (windowed and headless), includes it from the calling crate's `OUT_DIR`, watches its `watch_dirs` (the pass and include directories the build script was given) and lava-build-slang's `slang/`, and recompiles changed passes (a pass's `source` is its absolute path; any other changed file reloads every pass) with the same options on its own thread, then hands the SPIR-V to `lava::pipeline::reload_pass(index, spirv)`, which replaces the pass's module and pipelines in the `PipelineManager` (`lava/src/pipeline.rs`, the pass table types and every pass's pipeline cache) right away. There is one `PipelineManager`, which hands out raw `vk::Pipeline`s (a ray tracing pass's `RaytracingPipeline` with its binding table is lent to a closure); a reload swaps the new pipelines into its caches and retires the old ones, which are destroyed once no frame can use them (Epochs). Without the feature nothing watches and nothing is ever replaced. Changing a push-constant or specialization-constant layout (or the entry points) still needs `cargo build` so the bindings get regenerated: `BuiltPass.layout` hashes them (`compile::layout_hash`) and a reload whose hash differs is refused with an error, as is one the driver rejects (nothing is replaced then); reloading rebuilds every cached specialization.
- `shaders/compile.sh` → `shaders/bin/` is legacy and isn't used by the build.

## Tests (lava, lava-macros, lava-build-slang, lava-tests)
- `PATH=$HOME/.cargo/bin:$PATH cargo +nightly test -p lava -p lava-macros -p lava-build-slang -p lava-tests`. Add `--no-default-features` to test lava without `profiling` (lava-tests forwards it), and `-p lava-build-slang --features hot-reload` for the hot reload's watcher tests. Narrow with `-p lava --lib` (pure unit tests, no GPU), `-p lava-build-slang` (the compile helpers, plus the watcher with `--features hot-reload`), `-p lava-tests --lib` (the generated pass map), `-p lava-tests --test gpu_headless` (real GPU, headless, validation layer on, any validation error fails the test), `--test gpu_ray_tracing` (acceleration structures, ray queries and pipelines on a small scene, `lava-tests/shaders/include/ray_scene.slang`; skips without the features), or `--test gpu_window` (surface/swapchain/present; own `main`, opens a window briefly, skips without a display).
- Pure logic is tested in `#[cfg(test)] mod tests` at the bottom of each module. Never construct a `Buffer`/`Image` or call `Ctx::*` there: `Ctx::get()` blocks forever when lava isn't initialised.
- GPU tests share one context through `lava-tests/tests/common` (`gpu()` guard serialises tests and checks validation errors), so they can reuse the same bindless indices (0, 1, …).
- `core` has GPU-free unit tests (`cargo +nightly test -p core --lib`): the meshlet LOD build, the bake of a small glTF, both scene layouts, material files and slots, the `AssetIndex` layout behind `texture_index`, and the profiler's span capture and reports.
- **Lava's tests never use engine passes.** They live in `lava-tests`, an ordinary lava user: its `build.rs` compiles `lava-tests/shaders/*.slang` with lava-build-slang, and the tests import `lava_tests::bindings::*` and pass its `PASS_MAP` to `lava::init`. The generated bindings' tests (push constants, accesses) are in `gpu_headless.rs`, since slices and views need real buffers and images.
- `lava-tests/benches/bindings.rs` (`cargo +nightly bench -p lava-tests --bench bindings`, no GPU) compares `BindingOutput` layouts on models of core's frame and binding-heavy scenarios, all recorded through a copy of lava's barrier tracking. Compare ratios between variants, not absolute times, which move with the CPU clock. Under `generic_const_exprs`, a struct meant to unsize through its last field must hold its fixed arrays in non-generic newtypes: a `[u8; CONST]` field counts as depending on the struct's generics and blocks the coercion.
- Golden images live in `lava-tests/tests/golden/*.png`. A mismatch writes `<name>.actual.png`/`.diff.png` to `target/tmp/golden-failures/`. After an intended change to a test shader, re-bless with `LAVA_BLESS=1 cargo +nightly test -p lava-tests --test gpu_headless` and look at the PNGs.
- Slang gives shaders D3D-style `SV_VertexID`/`SV_InstanceID` (without `first_vertex`/`first_instance`).

## Commands
- After changing how meshes or textures are baked, run the `bake` tool with `--force` (see Headless tools).
- **Needs nightly.** `/usr/bin/cargo` (Arch stable) shadows rustup, so use `PATH=$HOME/.cargo/bin:$PATH cargo +nightly check` (or `build`/`run -p game`). Plain `cargo` fails with E0554. `.cargo/config.toml` sets `WORKSPACE_DIR` to the workspace root at build time; `core::WORKSPACE_DIR` and the paths under it (`core::ASSET_DIR` = `game/assets`, the baked files and the asset browser root; `core::UNBAKED_ASSET_DIR` = `game/unbaked_assets`; the editor font and `windows.ron` in the root) are baked in from it, so the binaries run from any working directory.
- `ash` and `ash-window` come from ash's git master through `[patch.crates-io]` in the workspace `Cargo.toml`, because the crates.io 0.38 release (April 2024) predates `VK_KHR_device_address_commands`; `gpu-allocator` is patched to its `ash-next` branch for the same reason (ash master renamed `push_next` to `push`, a `vk::TaggedStructure` method, and extension loaders from `new` to `load`). Bump all three together.
- Slang SDK lives in `lava/slang/` (gitignored). Linking goes through `.cargo/config.toml` (`SLANG_DIR` and rpath). lava-build-slang's `build.rs` links `slang-compiler` explicitly (into every build script and, with `hot-reload`, every binary using it) because `-lslang` would pick up the unrelated S-Lang library.

## Don't read
`target/`, `shaders/bin/`, `*.spv`, `*.glb`, `Cargo.lock`, `vulkaninfo.html`. These are binary, generated, or huge, and the project settings deny them.
