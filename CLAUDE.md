# GameEngine

Vulkan game engine in Rust (edition 2024, uses unstable `#![feature]`s), built on bevy 0.19 ECS **without** bevy's renderer.

## Orientation: read this before exploring
- A **code map** (each file's purpose, key types, and plugins, plus a shader table and live git state) is injected at session start by a `SessionStart` hook. Check it before running `ls`/`rg`.
- Full pub signatures and struct fields live in `.claude/context/api/{lava,core,game,lava-macros}.md`. Read the relevant file instead of grepping for an API.
- These files are generated by the `tools` workspace crate (`tools/`, no `#![feature]`s, so stable cargo works). To refresh them by hand, run `cargo run -q --release -p tools --target-dir target/tools`. It uses its own target dir so it never blocks on the main build lock, and it's cached by mtime.
- **Subagents don't get the hook output.** When delegating exploration, tell the subagent to read `.claude/context/codemap.md` first.
- Every `.rs` file starts with a one-line `//!` doc that feeds the code map. Keep it accurate when a module's role changes, and add one to every new file.

## Keep this context fresh (mandatory)
If you find that something in this file or the injected code map is wrong or out of date, or your change makes it wrong (new or renamed module, a moved responsibility, changed build steps or shader conventions), fix the source in the same task. Don't leave a note for later:
- Architecture, commands, conventions, gotchas → edit this `CLAUDE.md`. Keep it short and replace stale lines instead of appending.
- A file's purpose line in the code map → edit that file's `//!` line.
- Wrong or missing *generated* content (types, signatures, shader table) → fix `tools/src/main.rs`. Never hand-edit `.claude/context/*`, because it gets overwritten.
- Then rerun the `tools` generator (command above) and mention the context update in your summary.

## Crates (dependency order)
- `lava-macros`: proc macros for lava (validation tracing).
- `lava`: Vulkan abstraction over `ash` + `gpu-allocator`. Global `Ctx` state, bindless descriptors (`BindlessHandle`), `lava::init(Option<display>)` (`None` = headless), per-window `Surface` + `Swapchain` objects, usage-typed `Buffer`/`BufferSlice` and `Image`/`ImageView` (type-state generics `F: Format`, `U: *Usage`), `CommandBuffer` with automatic barrier tracking (every image access asks for `GENERAL`, except attachments, which are in `ATTACHMENT_OPTIMAL` while drawn to), and `RasterBuilder`/`compute`/`raytrace` dispatch.
- `core`: engine library made of bevy plugins wired in `core/src/lib.rs::CorePlugin`. It covers assets (the baked scene/mesh/texture files, their loaders, and the `bake` tool in `core/src/bin` that makes them from glTF), the render sub-app (pipelined, `ExtractSchedule`), a custom immediate-mode UI with docking, the editor (gizmos, picking, console, asset browser), physics (BVH raycasts), and the scene.
- `game`: the game binary (spawns a camera) plus the headless `render` tool in `game/src/bin` (see Headless tools).
- `tools`: dev tool that generates the Claude Code context (code map + API files) from the sources.

## Viewport
- With the editor, the scene is rendered into an offscreen image in the swapchain format (`ViewPortTarget` in `core/src/render/render.rs`) that starts at the initial window size and only grows; the scene uses its top-left `rect.size()` pixels, the passes get that size as an argument, and the tab draws it with matching UVs (`ViewPort.image_size`). `extract_view_port` writes its bindless handle into the main world's `ViewPort`, and the tab (`editor/viewport.rs`) draws it as a UI image. `ViewPort.rect` is the tab's content area; `hovered`/`focused` gate picking, drops and camera input.
- Without `EditorPlugin` there is no `ViewPort`, and the same passes draw straight into the swapchain image.
- Lava hands released bindless slots out again when an `Image` is dropped.
- An empty `DockingNode` leaf (`window: u32::MAX`) is just free space; a window dropped on it fills it.
- Since bevy 0.19 resources are entities: the Hierarchy tab lists them by type name (`IsResource`), the Selected tab edits the reflected ones like any component, and the Delete key skips them. To make a resource editable, derive `Reflect` with `#[reflect(Resource)]` (auto-registered); a field that can't be reflected needs `#[reflect(ignore, clone)]`, because the tab works on a `reflect_clone` of the value every frame.
- UI windows have no open/close calls: `ui.build(label, …)` requests a missing tab (created next `PreUpdate`), and `update_windows` closes every tab that wasn't built during the previous frame. `windows.ron` is only layout memory: a saved window (rect, tab group, dock slot) is created when one of its tabs is first requested, and dock slots nobody requested in the first frame are pruned. A reopened tab returns to its last rect; on exit only open windows are saved.

## Headless tools (use these to check your work)
- **Render to a PNG:** `PATH=$HOME/.cargo/bin:$PATH cargo +nightly run -q -p game --bin render -- game/scenes/sponza.ron /tmp/out.png`, then Read the PNG. The RON file gives image size, camera (`position`, `look_at`, `fov` in degrees) and `.scene` files with transforms; it waits until the scenes' meshes and textures are loaded too; `game/scenes/sponza.ron` is the template. Takes about 3 s for sponza. Write the PNG outside `target/`, which is denied for reading.
- It uses `HeadlessRenderPlugin { size }` (`core/src/render/headless.rs`), which only initialises lava: no window, swapchain, UI, console or render sub-app. Once the scene is loaded, `render_frame(main_world, &settings)` builds a throwaway render world, runs the extract systems on it once, draws the scene passes (`record_scene` in `render.rs`, shared with the windowed frame) into an RGBA8 image and returns the pixels.
- **Bake assets:** `PATH=$HOME/.cargo/bin:$PATH cargo +nightly run -q --release -p core --bin bake -- [--force] [FILE...]` turns every `.glb`/`.gltf` in `game/unbaked_assets` (`core::UNBAKED_ASSET_DIR`) that is newer than its baked scene into files in `game/assets`. It uses no bevy app and no GPU (sponza: about 50 s, 2.3 GiB peak memory, 462 MB baked). The meshlet build is not deterministic, so a rebake changes the mesh files (and a few pixels).
- Tracy is built with `ondemand`: without it the client buffers every span until a profiler connects, which grew the idle game by 10 MB/s.

## Baked files and the asset browser
- There is no bevy asset processor and no `.meta` file: `asset_plugin()` loads `game/assets` unprocessed, and only the `bake` tool (`assets/bake.rs`) writes there. `sponza.glb` becomes `sponza.scene` plus `sponza/meshes/<name>.mesh` and `sponza/textures/<name>.tex`, so every mesh and texture loads on its own. A bake deletes and rewrites the scene's whole directory.
- The files have no magic or version: after changing a layout (or the `Material` struct), bake with `--force`. They are written with the `write_slice`/`write_compressed` helpers in `assets/mod.rs` and read back front to back through bevy's async `Reader` (`read_slice`/`read_compressed`); big payloads are zstd-compressed.
- `.scene` (`SceneFile` in `assets/mesh.rs`): instance transforms, materials with scene-local texture indices, names, and the paths of its meshes and textures relative to its directory. `SceneLoader` loads those with `load_context.load`, so they arrive after the scene.
- `.mesh`: `MeshHeader`, the compressed GPU data, the compressed collision BVH. `.tex`: `TextureHeader`, a `PREVIEW_SIZE` RGBA8 preview, then one compressed mip after the other. Textures are BC7 (`TextureKind::Color` sRGB, `Data` linear) or BC5 (`Normal`, the shader reconstructs z), chosen by the material slot that uses the image.
- The browser (`editor/asset_browser.rs`) shows the files of `ASSET_DIR` as they are and keeps no per-tile state: only the rows in view are laid out, and a click opens a folder. A `.tex` tile in view reads just its preview from the file, synchronously, into one main-world atlas image (`Previews`, written by `Image::copy_region_from`); the atlas holds 1024 previews and the least recently shown makes room.
- The browser never polls. A `notify` watcher on `ASSET_DIR` forwards every changed path (access events are ignored): the path's preview is forgotten, and a change directly inside the open directory re-reads it.
- Dragging carries an `AssetDrag` (`ui/dragdrop.rs`), which loads the asset only when a drop target takes it (`drop_in_viewport`, the inspector's handle slots).

## Materials
- Each loaded scene owns one `MaterialSet` asset (`assets/mesh.rs`): all its materials in one host-mapped buffer, plus one `MaterialTextures` (the five optional texture handles) per material, which keeps them alive and is how a material's textures are found. An `Instance` holds the set handle and an index; the renderer only writes one material address per instance per frame (`InstanceManager.instance_materials`, `Buf<Material *>` in `raster.slang`). A mesh dropped from the browser gets its own one-material set. Textures load after the set: `resolve_material_textures` (`scene/mod.rs`) writes their bindless indices into the buffer when a texture or set arrives, until then a slot is the null handle (`NO_TEXTURE` in the shaders).
- `MaterialSettings` exists only on `Selected` instances (systems in `scene/mod.rs`): it is read from the set's buffer on selection, edits are written straight back into that memory, and it is removed on deselect. Instances sharing a material index share the edit.
- `Material` (`shaders/include/datatypes.slang`, mirrored by `MaterialSettings`) is baked into `.scene` files, so changing it needs a bake with `--force`. There is no blending: `alpha_cutoff` discards fragments in `raster.slang`. The importer sets it to 0 for opaque glTF materials, and to the default 0.5 for blended ones and for masks with a cutoff of 0.

## Shader pipeline
- Source: `shaders/passes/*.slang` (one file = one pass) and `shaders/include/*.slang`. `shaders/old/` is dead code.
- `lava/build.rs` compiles each pass with `shader-slang`, writes SPIR-V to `$OUT_DIR/passes/`, and reflects the `[[vk::push_constant]]` struct to **generate `lava/src/bindings.rs`** (gitignored, never edit it). For example, `raster_outline.slang` → `RasterOutline::new(...)` returns a `BindingOutput` that you hand to `cmd.raster()...draw()` / `cmd.compute()`.
- Matrices use column-major layout (`matrix_layout_column` in both `build.rs` and the hot-reload session in `command_buffer.rs`), so a glam `Mat4` arrives untransposed and shaders write `mul(M, v)`.
- Push-constant field types map like this: `Buf<T>`/`MutBuf<T>` → `BufferSlice<T, U: IsStorage>`, and `Img` → `ImageView` (bindless handle). Inside structs behind a `Buf`, `Img` and `DynImg` fields become a `BindlessHandle`. `Img` and `DynImg` have `GetDimensions()`. `DynImg` (`bindless.slang`) reads whichever of the sampled/storage index isn't `NULL_HANDLE`; the UI pass uses it for `UIVertex.texture`, and images referenced this way get no automatic barrier: register them on the pass with `BindingOutput::{sampled_read, storage_read, storage_write, buffer_read, buffer_write}` (each returns a `BindingOutput` one entry larger, which is why `lava` and `core` enable `generic_const_exprs`). Entry-point names must be unique per stage across all passes.
- Runtime hot reload: `lava/src/command_buffer.rs` watches `shaders/` and recompiles changed passes. Changing a push-constant layout still needs `cargo build` so the bindings get regenerated.
- `shaders/compile.sh` → `shaders/bin/` is legacy and isn't used by the build.

## Tests (lava, lava-macros)
- `PATH=$HOME/.cargo/bin:$PATH cargo +nightly test -p lava -p lava-macros`. Narrow with `--lib` (pure unit tests, no GPU), `--test gpu_headless` (real GPU, headless, validation layer on, any validation error fails the test), or `--test gpu_window` (surface/swapchain/present; own `main`, opens a window briefly, skips without a display).
- Pure logic is tested in `#[cfg(test)] mod tests` at the bottom of each module. Never construct a `Buffer`/`Image` or call `Ctx::*` there: `Ctx::get()` blocks forever when lava isn't initialised.
- GPU tests share one context through `lava/tests/common` (`gpu()` guard serialises tests and checks validation errors).
- `core` has GPU-free unit tests for the meshlet LOD build (`cargo +nightly test -p core --lib assets::mesh`).
- **Lava's tests never use engine passes.** They render with their own passes in `lava/tests/shaders/*.slang`, compiled only with the `test-passes` feature (enabled by lava's self dev-dependency). With that feature `build.rs` writes the bindings to `$OUT_DIR/bindings.rs` and leaves `src/bindings.rs` alone.
- Golden images live in `lava/tests/golden/*.png`. A mismatch writes `<name>.actual.png`/`.diff.png` to `target/tmp/golden-failures/`. After an intended change to a test shader, re-bless with `LAVA_BLESS=1 cargo +nightly test -p lava --test gpu_headless` and look at the PNGs.
- Slang gives shaders D3D-style `SV_VertexID`/`SV_InstanceID` (without `first_vertex`/`first_instance`).

## Commands
- After changing how meshes or textures are baked, run the `bake` tool with `--force` (see Headless tools).
- **Needs nightly.** `/usr/bin/cargo` (Arch stable) shadows rustup, so use `PATH=$HOME/.cargo/bin:$PATH cargo +nightly check` (or `build`/`run -p game`). Plain `cargo` fails with E0554. The asset paths in `core/src/lib.rs` are absolute (`core::ASSET_DIR` = `game/assets`, the baked files and the asset browser root, and `core::UNBAKED_ASSET_DIR` = `game/unbaked_assets`).
- Slang SDK lives in `lava/slang/` (gitignored). Linking goes through `.cargo/config.toml` (`SLANG_DIR` and rpath). `build.rs` links `slang-compiler` explicitly because `-lslang` would pick up the unrelated S-Lang library.
- Profiling: tracing + tracy (`tracing-tracy`).

## Don't read
`target/`, `shaders/bin/`, `*.spv`, `*.glb`, `Cargo.lock`, `vulkaninfo.html`. These are binary, generated, or huge, and the project settings deny them.
